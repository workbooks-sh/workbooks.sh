Decision 1 — Top-level type taxonomy (p0.10): kit · app · agent as co-occurring facets

"Has-interface" is the wrong cut — every work-* workbook renders, so it partitions nothing. The load-bearing axis is library-vs-leaf (import-vs-launch), npm's exports-vs-bin split. And types are a SET, not an enum: library.ex:536 already states "a toolkit IS a workbook," so one .html can be both a launchable app AND export a kit.

Minimal facet set, declared as zero-or-more TYPE edges (the spine's existing form — work-ref.js:68-69):

  1. <work-ref rel="kit" as="crm"> — exports a <prefix-*> element/command library (the floor; untagged-with-exports defaults here)
  2. <work-ref rel="app"> — a launchable leaf interface (gets a route/window)
  3. <work-ref rel="agent"> — carries a runnable brain (<work-agent> + <work-src>)

Drop skill from the rel vocab (skills are kit CONTENTS, not a type) and drop container entirely (it is an execution tier of isolation*.ex, not a type). Action: edit work-ref.js:7-8 header vocab to rel=kit|app|agent.

Decision 2 — Loader migration plan (p0.1): one Floki pass over the type edge

Today work_kits.ex:48 discovers via the <work-toolkit> ELEMENT; node_of/1 (:1594) pattern-matches only that tuple, so the already-migrated workkits/work/manifest.html (the lone rel="kit" manifest) parses to ZERO nodes today.

  1. Add kit_nodes/1: Floki.find("work-ref[rel=kit]"); node_of accepts BOTH tuples; alias name→id, pull doc from sibling <work-doc>.
  2. Map sibling <work-ref rel="needs" to=…> → {:dep, to, to} tokens, union with the legacy requires= attribute (CLI pre-flight tokens stay on the attribute).
  3. Keep <work-toolkit> as a parsed fallback (nodes = kit_nodes ++ legacy) so the 29 unconverted manifests keep working.
  4. Gate via the 3 existing toolkit tests (descriptor / graph / discovery) feeding BOTH forms; convert the 29 manifests in a separate batched commit; then DELETE the fallback (Golden Rule 5).

Verified: 29 manifests on <work-toolkit>, exactly 1 on rel="kit". All HTML, no JSON.
