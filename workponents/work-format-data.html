Data — a resource is the database

Describe a thing once. The server stores it, the client calls it, and the page stays live. No schema dialect, no API, no glue.

A resource is a kind of thing your workbook keeps — leads, deals, tasks. You write what it is; everything else is generated. The vocabulary is WIT's own — what you author is what runs and what you debug.

The floor — just the shape

This alone is a working database table. You get create, read, update, delete, and reactive reads — for free.

resource Lead do
  name     :text
  revenue  :money
  status   :new | :enriched | :scored   # an enum, inline
  tags     [:text]                          # a list
end
createreadupdate deletelive queriesvalidation

You name fields by what they mean — :money, :text, an inline enum — and the type, the validation, and the way it renders all fall out of that meaning. No field :revenue, integer() ceremony; no guessing a type from a default.

A pure value is a record, not a resource

Some shapes have no identity and no behavior — they're just values that live inside a resource. Those are records.

record Money do
  cents     :int
  currency  :usd | :eur | :gbp
end

WIT already draws this line: a record is a value, a resource is a stateful entity with operations. We use the same words, so the contract and the debugger speak your language too.

Reads and writes — only when you need a custom one

The defaults cover most of it. When you want a named view or a transactional change, write it inside the resource.

resource Lead do
  name     :text
  revenue  :money
  status   :new | :enriched | :scored

  query :hot, where: status == :scored and revenue > 50_000

  mutation :enrich do             # runs server-side, transactionally
    fetched = Dock.fetch(crm_url(name))
    %{revenue: fetched.revenue, status: :enriched}
  end
end

A query is a live view — when the data changes, every page reading it updates, no reload. A mutation is an all-or-nothing change. Same idea as the rest of the format: the page isn't a snapshot of the store — the page is the store.

Where it runs — server owns the data, client calls it

Server — the database

The resource is the database: it stores rows, runs queries and mutations, validates, and swaps backends (SQLite → Postgres) without a rewrite. The client never runs a database.

Client — a typed reference

The browser gets the shape and calls the resource's operations across the WIT boundary. It renders the live result. It holds a view, never the source of truth.

resource Lead (you write it, once)
  → server: the live database + queries + mutations
  → client: the typed shape + calls over WIT
  → a change on the server → the client view updates, live

So the whole database is just things you describe in the document. The shape is shared, the data is server-authoritative, the page is live — and you never wrote an API, a serializer, or a line of state-sync.
