Native leverage — the HTML5 + CSS surface for workbooks

The bet: HTML already carries structure & state, CSS already carries views & queries, so our work-* layer only adds compute & typed edges. The more native does, the less we invent — and the more an agent already knows the syntax. This maps the whole surface, with an honest readability verdict on each.

Two rules hold it together. (1) A work-* element exists only where native has no equivalent — <template> already exists, so there is no work-template; the survivors are just work-src / work-ref / work-flow + the live/queryable kits. (2) Never over-scope native — <details> is disclosure for anything, not "agent disclosure"; <ol> means sequence in a flow but is never restricted to one. Recognize meaning by context; don't impose it. Smaller engine, fully legible.

HTML structure

ol/ul/details/dl — sequence, parallel, disclosure, k/v. The tree IS the flow.

HTML state

input/form/output — done-ness, params, validity. Native state, no JS.

HTML relations

link[rel]/a[href]/meta — the web's own tagging + edges. work-ref generalized.

CSS views

[attr]/:has/:state — a "view" is a selector. The board is a stylesheet.

The SVG-confusion question (read this first)

Your worry: does this become opaque coordinate-soup like <path d="M12 2L2 7…">? No — and the reason is structural. SVG is presentational geometry: its attributes are numbers with no meaning to a reader. A workbook is semantic structure: every tag is a meaningful noun (<ol>, <input>, <work-src>) and every attribute is a word (rel="needs", status="done"). You can read it aloud. The one place it gets denser is a work-ref edge with rel/cond/to — but those are sparse (only where the flow bends) and read like a <link rel> or <a href>, which every agent already knows. Rule we hold: lean on semantic elements; never encode meaning as coordinate/opaque attributes or data-* soup. If a block stops reading like a sentence, that's the smell.

2 · Context & narrative literate programming, native

The under-used leverage: a workbook IS a document, so you write the why around the what as HTML prose interleaved with work-src — richer than a // comment, richer than markdown (bold, links, lists, headings, even embedded work-*). An agent writes reasoning and runnable code in the same breath.

<figure> <figcaption>THE "code + its explanation" unit — a captioned, referenceable code block. The figure runs; the caption says why.
<figure>
  <work-src lang="rust">fn connect()…</work-src>
  <figcaption>pooled so a retry reuses the socket</figcaption>
</figure>

4 · Tagging & relations the web already IS our edge system

This is the deep one: link[rel], a[href], and meta are the native "typed relation to a resource" + "document facts." Our work-ref rel= / tagging=C is literally these, generalized — and the microformats rel registry is the prior art.

<link rel>a TYPED relation — the native tagging. A workbook declares its type/deps the web's own way.
<link rel="kit" href="#self">
<link rel="needs" href="cloudflare">

[id] · [hidden] · [inert]node identity; a not-yet-active node (hidden); a blocked subtree (inert — present but disabled).

Capstone — all of it in one readable file

A cron'd research workflow that is also a checklist also a board — read it top to bottom. Native structure (ol/ul/details), native state (checkbox), one edge where it loops (work-ref), one CSS view (the board), tagging via link[rel]. Nothing reads like SVG.

<link rel="app" href="#self">
<work-flow name="auto-research">
  <meta name="work:every" content="6h">          <!-- cron -->
  <ol>                                            <!-- ordered ⇒ sequence -->
    <li><input type="checkbox"> pick a topic
        <work-src lang="js">return pickTopic()</work-src></li>
    <li id="search"><input type="checkbox"> search
        <work-src lang="js">return await search(topic)</work-src>
        <work-ref rel="when" cond="hasMore" to="search"/>   <!-- the one loop edge --></li>
    <li><ul>                                       <!-- unordered ⇒ run in parallel -->
          <li><agent>angle A</agent></li>
          <li><agent>angle B</agent></li>
        </ul></li>
    <li><details><summary>write-up</summary>
          <agent>summarize the findings</agent></details></li>
  </ol>
</work-flow>

<style>  /* the "board" view — pure CSS over the same nodes, no component */
  li:has(:checked)       { /* → Done column */ }
  li:not(:has(:checked)) { /* → To-do column */ }
</style>
