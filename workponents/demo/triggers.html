data-trigger · the trigger grammar

One attribute says when a flow runs — modeled on HTMX hx-trigger. load fires on connect, every Ns polls, visible waits for scroll, and <event> from:#id chains off another element's events. The chaining below is the whole point: flow B starts the instant flow A emits work-flow-done — declarative choreography, zero glue code.

1 · data-trigger="load" — flow A autoruns on connect

  1. await sleep(250); ctx.rows = [10,20,30,40]; return `fetched ${ctx.rows.length} rows`;
  2. ctx.clean = ctx.rows.filter(n => n >= 20); return `kept ${ctx.clean.length}`;

2 · data-trigger="work-flow-done from:#flow-a" — flow B CHAINS off A

  1. await sleep(200); ctx.total = [10,20,30,40].filter(n=>n>=20).reduce((a,b)=>a+b,0); return `sum of A's kept rows: ${ctx.total}`;
  2. return `report ready · ${ctx.total}`;
↓ scroll down — the next flow waits until it's visible ↓

3 · data-trigger="visible once" — flow C runs only when scrolled into view

  1. await sleep(150); ctx.primes = [2,3,5,7,11,13]; return `computed ${ctx.primes.length} primes (only ran because you scrolled here)`;
