Why your secrets never touch the OS

You can let an agent run real, untrusted code — and still keep the one thing you can't afford to lose on the far side of the wall.

June 13, 20264 min read

If you give a coding agent access to your operating system, you've given it access to nearly everything. It can run a shell, which means it can read any file, reach any service your machine can reach, and find its way to your keychain, your environment variables, your saved credentials. For one person on their own laptop, that's usually fine. The instant you're handling proprietary data — a customer's, a client's, your own company's — that open box becomes a real liability.

The common fix is to rent isolation: a micro-VM from E2B or Daytona, a Firecracker instance, a Mac mini in the corner running an agent around the clock. They work. They are also expensive, Linux-shaped, and they don't actually answer the hard question — they just put a wall around the danger and keep the dangerous thing inside it.

Workbooks answers differently, and the difference is the whole point of this post.

powers don't leak in by accident

A workbook runs inside WebAssembly — the same isolation the browser has relied on for years, here running server-side on wasmtime. Inside that sandbox a workbook starts with nothing. No network, no secrets, no ability to send a message. When the host starts a run, it picks a profile: a short list of plain words naming exactly which powers this run gets. The host picks it, never the file — a workbook cannot grant itself anything. As it loads, the host wires in only the abilities on that list, one word at a time.

This matters because an ungranted power isn't denied — it simply doesn't exist in the workbook's world. There's no check to slip past, because there's no function to call. A workbook never granted the network doesn't get a quiet "no" when it reaches out; it never had the network to reach with. The decision happens before it runs a single instruction.

Grant the verb. Keep the noun.

the secret stays on the host's side

For the sensitive powers there's a second move, and it's what makes them survivable to grant. Everywhere else, "let the code use the key" has meant "give the code the key" — and from that moment it's lying around in a file, a variable, a log, forever. A workbook refuses that bargain. With secrets granted, a workbook can name and use a secret, but never read it.

The sharpest form of this is signing. The workbook asks the host, "sign this for me." It sends the data across; the host stamps it with the secret; the workbook gets back a signature — having never held the key. The same inversion covers the rest. Calling a language model? The host holds the account key and pays the bill; the workbook gets the answer, never the credential. Fetching a web page? The host owns the connection, refuses internal addresses, caps and audits each response; the workbook hands over a destination and receives the page, never a socket.

That's the literal meaning of the title. Your API keys live where the host keeps them. They are used on your behalf and never copied into the place where untrusted code runs.

the honest worst case

Every real conversation about security ends at one blunt question: if this thing turns hostile, what's the worst it can do? Prompt injection is the live version of that — a stray sentence on a web page talks your agent into exfiltrating something.

Here is the honest answer, not "every power, none of the danger." Even fully fooled, the agent still can't read your Stripe key — it was never in its world to read. What it can do is use the secret through the host's broker, where every request is rate-limited and audited. That's a real exposure, and worth saying plainly: a fooled agent with the secrets power can make the host sign or send things it shouldn't. It cannot walk off with the key itself. The danger that remains is bounded, leashed, and logged — not unlimited.

One correction worth pinning, because an earlier telling of this got it wrong: the everyday minimal profile is not a sealed scratch space. It grants secrets and brokered sockets too. The genuinely sealed rung is the pure-compute floor — disk and nothing else — which is also where the system falls back if you ask for a profile that doesn't exist. It fails closed, not open.

grant it, then take it back

The last piece turns "handed over deliberately" into a practice you can actually run. Because the host hands out abilities rather than baking them in, it can revoke one mid-flight. The next time the workbook tries to act on a revoked power, the action simply fails. Granted is not permanent — it's a leash the host is always holding.

So the working skill is small. Before a run, choose the lowest rung that still lets the workbook do its job: the sealed compute floor for pure data work, minimal to remember and run commands, the network rung only if it truly must reach the world. Grant deliberately. Pull it back the moment you don't trust where it's going. The powers are real; the danger sits where the workbook can't reach it; and the choice stays in your hands.
