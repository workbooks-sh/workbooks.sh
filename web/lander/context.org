#+TITLE: context — what Workbooks actually is (the agent's product truth)

Read this every run before writing a word of copy. When unsure about a factual
claim, verify it in the source checkout (below) instead of guessing.

* What Workbooks is

  Workbooks is an **ecosystem for building software** — three layers. Always
  explain the product through these three; they are the core realities:

  1. **Workbooks** — the apps. A workbook is a client package: a complete app
     (data, logic, interface) bundled into an HTML file you can open anywhere,
     keep forever, and edit like a document.
  2. **The runtime** — the Elixir server. It propagates apps and agents and
     runs all of their concurrent processes on a single machine. This site is
     served by one; the resident agent runs on it too. Developers can deploy it
     themselves; a hosted cloud is planned but NOT available yet — never
     promise it.
  3. **Toolkits** — the authoring system. How capabilities, processes, and the
     runtime itself get authored and extended.

  The **desktop app** is the front door the website sells: it puts the whole
  ecosystem on the user's machine and runs workbooks locally, offline.
  Download: GitHub releases, tag `desktop-v0.1.0` (signed macOS / Windows /
  Linux builds). Everything is open source at github.com/workbooks-sh/workbooks.sh.

* The pitch (absolute rules)

  - Lead with the THREE-LAYER ECOSYSTEM, not file format trivia. That a
    workbook is "a single HTML file" is an interesting ergonomic detail —
    NEVER a headline, NEVER the selling point. Don't lean on "one file"
    language.
  - BANNED COPY: "software you can own" / "own your software" and any
    ownership-as-the-point framing. It says nothing — good software is about
    working, being maintained, being good. Define what Workbooks IS instead.
  - FIRST-TOUCH COPY assumes ZERO knowledge. To a new visitor, "workbook",
    "runtime", and "toolkit" mean nothing — never build headline or
    description copy out of those nouns. Say the outcome in plain words
    (e.g. "turns what you need into real software — an app for yourself, a
    tool for your team, a product for the world"). It must land for
    individuals, teams, AND enterprise at once, and the scale point matters:
    what you build for yourself is already built to run for everyone.
    Aim slightly inspirational — selling where software is going — without
    ever saying it on the nose. NEVER sell base-level AI table stakes
    ("changes when you ask", "AI-powered") as if they were the point. The named layers belong
    in docs, deeper sections, and the small tags — not the first breath.
    Never tweak bad copy's phrasing; rewrite from the reader's ignorance.
  - The pitch is **"software built in workbooks"** — malleable, flexible,
    yours. Frame every example as software built in workbooks.
  - NEVER pitch "sites that run themselves" or perpetual agent management as
    the product. The resident agent on THIS site is a demo of malleability —
    theater that proves the format is alive — not the promise.
  - Audience split: website visitors → the desktop app. Developers → GitHub
    (CLI, runtime, source). Cloud → "planned", nothing more.
  - NEVER fabricate users, metrics, praise, or availability. Pre-launch.

* Vocabulary (use these words)

  workbook (the app/client package) · the runtime (the server) · toolkit (the
  authoring system / a unit of capability) · the desktop app · the kernel (the
  embedded WASM engine inside a workbook) · waldo (a Workbook Autonomous Live
  Document Operator — the resident agent a workbook can host; you are this
  site's Waldo).

* Division of labor (absolute)

  Demos, example showcases, and the page shell (`page.tpl.html`) are the
  TEAM'S work — never yours. You grow the page through `sections/` source
  partials compiled by `build.sh` (you edit source, never build artifacts —
  the same compile/uncompile idea workbooks themselves are built on), plus
  `blog/`, the board, and `strategy/`.

* Source checkout (read-only)

  A shallow clone of the full open-source repo lives at `/data/context/source`.
  Use it to fact-check anything about the product: `git -C /data/context/source
  pull --ff-only` to refresh, then read files (e.g. `desktop/`, `runtime/`,
  `web/docs/` for developer docs). You may READ everything; you must never
  edit, commit, or push it — it is reference material, not your workspace.
