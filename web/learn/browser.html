so where do you actually Use a workbook?

You've met the workbook — one file that is whole software. You've met the Nexus — the engine that brings it alive. But there's a plain question underneath both: when you sit down to work, what's the window in front of you? A normal browser can open a workbook as a page, but it doesn't know what a workbook is — it can't weave one, dock one into your engine, or keep your workspace of them.

Every application you use has a front door. For email it's the inbox; for the web it's the browser — tabs across the top, a back button, a place to type an address. You don't think of the browser as "an app." You think of it as the place the other apps live.

Workbooks has a front door too. And here's the quietly radical part: the front door is itself a workbook.

the DEFINITION

brows·er /ˈbraʊ·zər/ noun

1. a desktop application — for Mac, Windows, and Linux — whose own interface is built out of workbooks: it opens, weaves, and runs them, holds your workspace of them, connects to an engine, and lets any toolkit mount its own piece of interface inside it.

The shape is familiar on purpose. Tabs, bookmarks, a file tree, an address you can share — the muscle memory of a web browser, pointed at workbooks instead of web pages. What's new is everything behind the right edge.

That's the whole idea. Everything below is unpacking it.

what it's MAde of

Strip the Browser to its frame and it's a small, familiar set of parts — nothing exotic. The exotic part is the right-hand side, and it gets its own section.

That last line is the move. In normal software there are two worlds: the app, which only its makers can change, and your stuff, which lives inside the app's walls. You can rearrange your stuff; you cannot rearrange the walls. The Browser erases that wall — the walls are made of the same material as the stuff, so the same moves that reshape a workbook reshape the app around it.

the DOCK — where the app grows new limbs

Along the right edge is a dock: an open strip where any toolkit can mount its own panel. Remember what a toolkit is — a safe bundle of real abilities you hand to a workbook. Here a toolkit can also bring its own piece of interface and hang it in the dock, themed to match everything around it.

The consequence is strange and wonderful: the way you add a feature to the Browser is to write a toolkit. An agent — Claude Code, say — can pick an icon, write a small toolkit, and a new panel simply appears in the top-right corner of your app. No app store, no update, no waiting for the makers. The application grows a new limb because you (or the agent working with you) decided it should.

Extensible to its core. Most apps offer "extensions" as a fenced-off sandbox bolted onto a frozen core. Here the core and the extensions are the same kind of thing — workbooks and toolkits — mounted in the same dock, drawn with the same theme.

The left navigation works the same way: it's composable, built from presets you can rearrange, not a fixed menu someone shipped.

toolkits drive the BROwser

depth rung · skippable — skip to the resident agent if you just want the gist

For the dock to be more than decoration, a panel needs to actually do browser things — open a tab, drop a bookmark, read what's in the viewer, react when you switch documents. The browser SDK is the small set of controls the Browser hands to its toolkits: tabs, bookmarks, viewer state, events.

So a toolkit isn't just painting a panel; it can drive the surface it lives in. A research toolkit can open three tabs and arrange them. A reading toolkit can watch which workbook you're viewing and follow along. In effect, an agent can build you your own desktop app out of these parts — and because it's all workbooks and toolkits, it's the same craft you've already learned, pointed at the app itself.

There's a matching seam underneath: an embedded control channel lets an assistant like Claude Code drive the Browser directly — open things, arrange panels, watch what happened — so the app can be operated by an agent, not just by a cursor.

the agent that LIVES here

Because everything you learned about agents is true here too, the Browser comes with one already living inside it — a resident agent you can talk to about the thing in front of you. It isn't a separate chatbot in a corner; it's wired into the same dock, the same SDK, the same engine connection. It can open things, weave things, and file work for itself when it notices something that should change.

The agent and the app are not two products glued together. The agent is just another thing mounted in the same surface — the most active resident of a building made of workbooks.

how you GEt it

The Browser ships with the command-line tool. There's no separate download dance and no in-app setup wizard to click through — the one command you met on the CLI page installs and opens it. The CLI owns setup; the Browser owns the work.

And because an agent can drive the whole surface through the SDK, an assistant can install it, open it, and start arranging it for you — set your theme, lay out your panels, pick your starting tabs — before you've touched the keyboard.

why this is the last TUrn

It's fitting that the Browser comes near the end of the path, because it only lands once everything before it is in place. A workbook is one file. It speaks one plain language. It gets abilities through toolkits. It comes alive on an engine. Agents work inside it. Plans run themselves.

Take all of that and point it at the application itself, and you get the final, almost recursive idea: the tool you use to build with workbooks is built out of workbooks. There is no privileged layer, no frozen core you're forbidden to touch. The front door is made of the same material as every room behind it — which means the moment you understand a workbook, you already understand the thing you're using to hold one.

(Worth keeping straight: this is the Browser, the app you work in. It's a different thing from browsing — the sandboxed ability a workbook has to fetch a web page from inside the engine. Same word, two ideas.)

questions people actually ASK

Is this just a wrapper around Chrome?

No. It's a desktop app built for workbooks — its interface is itself assembled from workbooks, and its job is opening, weaving, running, and organising them, with a live connection to an engine you own. A normal browser can render a workbook as a page; it can't do any of that.

Do I need the Browser to open a workbook?

No — a workbook still opens in any ordinary browser, for anyone, forever. The Workbooks Browser is for building, organising, and running workbooks as a daily workspace; it's never a gate on simply viewing one.

How do I add a feature to it?

You write a toolkit — or you ask an agent to. A toolkit can bring its own panel, themed to match, and mount it in the dock through the browser SDK. That's the whole extension model: no app store, no update cycle, no privileged plugin API separate from how everything else is built.

What's the dock, exactly?

The open strip along the right edge where toolkit panels mount. Each panel can read and drive browser state — tabs, bookmarks, the viewer, events — so a panel is a real participant in the app, not a static widget.

Is it finished?

It's active, fast-moving work — the core (tabs, viewer, file tree, bookmarks, engine connection, theming, the dock, the resident agent) is the spine, and the surface is deliberately the part that keeps growing, because growing it is the point.
