one parser, or it's a LIE

The org lesson makes a strong claim: the written layer is parseable, testable, machine-checkable. The cheap way to "demo" that is a lookalike — a few regexes that handle the happy path and quietly disagree with the real grammar on everything else. That kind of demo teaches you a dialect that doesn't exist.

So this page refuses the cheap way. The parser running here is the kernel — the exact Rust crate the engine uses to parse every workbook, every manifest, every deployment file. One grammar needs one brain, and you're about to poke it.

how a kernel gets into a PAGE

The kernel is one source file with no idea where it's running. It compiles three ways, and this page is the third:

That third build is why a workbook can be honest about being runnable: browsers execute WebAssembly natively, so the file's own brain travels with it. This page is a small proof of the workbook thesis wearing a notebook costume.

first CONTACT

Here's real org — a tiny project plan. States are TODO and DONE keywords; the dependency lives in a properties drawer, the canonical way to attach data to a headline. Edit it freely.

* TODO ship the landing page
** DONE write copy
** TODO render hero art
** TODO build page
   :PROPERTIES:
   :DEPENDS: render-hero-art
   :END:

Two panes, one truth: the source on the left is the file; the document on the right is the kernel's render() of it, refreshed as you type. Now ask the kernel what it sees — not text, structure:

const rows = nb.oql.headlines(nb.org("plan"));
for (const h of rows) {
  const dep = h.props.DEPENDS ? "   depends on: " + h.props.DEPENDS : "";
  print(`level ${h.level}  ${h.state || "(no state)"}  ${h.title}${dep}`);
}
return rows.length + " headlines, parsed canonically";

Try earning the parser's attention: add a headline, give one a DEADLINE: <2026-07-01> line, misspell :PROPERTIES: — then parse again and watch what structure survives. That's the difference between a grammar and a convention.

the LIVING document

Look at the document pane again — the task headlines grew checkboxes. They're not decoration. Tick one. The source flips between TODO and DONE, and the change is narrated under the cell in words anyone understands.

This is the whole CMS thesis of the ecosystem in one interaction: the document is not a view of the data — the document is the data. A checkbox in a rendered page, a line in a plain-text file, and a state the engine schedules around are the same fact in three outfits.

Where you've seen this before: every site page on workbooks.sh is itself authored as org and rendered by this same kernel on the engine. You're holding the client-side end of the exact pipeline.

break SOMETHING

Parsing is half the job; judging is the other half. Below is a workflow — the real shape the engine deploys: a tagged headline whose component children carry source blocks with inputs and outputs.

* site build                                  :workflow:
** render                                     :component:
#+begin_src js :out page
export const page = () => "hello";
#+end_src
** publish                                    :component:
#+begin_src js :in page :out site
export const publish = (p) => "deployed: " + p;
#+end_src
  
const diags = nb.oql.validate(nb.org("flow"));
if (!diags.length) { print("clean — every input has a producer, every component has a language"); return; }
for (const d of diags) print(`${d.level}: ${d.scope} — ${d.message}`);

Now sabotage it: change :in page to :in pages and validate again. The kernel names the component and the missing producer — the same diagnostic that would stop a bad deploy on a real engine. You can't write a test suite for Markdown. You just watched one run for org.

the honest BOUNDARY

What you've touched runs entirely in this tab: parse, render, validate, the two-way document. What this page can't do is the living part — persist your edits, run the plan on a schedule, let an agent tend it overnight. A browser tab has no clock you can leave running and no disk you can trust.

That's not a limitation of the kernel; it's the seam the whole system is built on. The file thinks. The engine lives. Same kernel on both sides of the seam.

the RECIPE

Everything this page does, as a prompt your agent can implement against your own grammar or toolchain:

the recipecopy it to an agent, or read it as the spec
Embed a real parser in a web page and build a two-way living document.

Build: compile the project's canonical parser to WebAssembly with a minimal
ptr/len ABI (alloc, dealloc, and string-in/string-out exports — pack pointer
and length into one u64 return). In the page: instantiate the wasm, wrap the
exports in small JS functions, and mount editable source cells whose
rendered view refreshes on edit.

Make the rendered view interactive: pair the renderer's output with the
parser's structural rows (same document order) to attach controls — e.g.
checkboxes on stateful items. A control edit rewrites the SOURCE (the
document is the data), then re-renders, and narrates the change in plain
words ("checked off: render hero art").

Requirements:
- The browser build must be the same parser source the production system
  uses — no demo dialect.
- No framework, no server round-trips; the wasm is a static asset.
- Validation runs client-side too, with diagnostics that name the failing
  node.

Acceptance: editing source updates the view; toggling a control updates the
source text exactly; and a deliberately broken input produces the same
diagnostic the production system gives.
