Every piece of software you use has a front door. For email it’s the inbox. For the web it’s the browser — the window with tabs across the top, a back button, a place to type an address. You don’t think of the browser as “an app.” You think of it as the place the other apps live.

Workbooks has a front door too, and it’s the most quietly radical idea in the whole system: the front door is itself a workbook.

The app made of the same stuff

Up to now, a workbook has been the thing you make — a file you hold, weave, give powers, deploy. The Browser flips the camera around. The application you use to open those files, to weave them, to watch them run — that application is also built out of workbooks. The screen you’re looking at is not a fixed program someone shipped once and froze. It’s the same kind of living document you’ve been learning to build.

That sounds like a parlor trick until you sit with what it removes. In normal software there are two worlds: the app, which only its makers can change, and your stuff, which lives inside the app’s walls. You can rearrange your stuff; you cannot rearrange the walls. The Browser erases that wall. The walls are made of the same material as the stuff, so the same moves that reshape a workbook reshape the app around it.

What it actually gives you

Strip it down and the Browser is a small, familiar set of parts:

  • Tabs — open many workbooks at once, flip between them like web pages.
  • Bookmarks — keep the ones you return to.
  • A file tree — your workspace on the left, the documents and disks you’re working with.
  • A viewer — the panel that opens a workbook and shows its screen, running live, right there.
  • A connection to an engine — the same Nexus from earlier; plug in and the workbooks in your tabs stop being documents and start being living services.
  • Theming — the whole surface takes on a look, down to the color of a single tab.

None of that is exotic. The exotic part is the right-hand side.

The dock: where the app grows new limbs

Along the right edge is a dock — an open strip where any toolkit can mount its own panel. Remember what a toolkit is: a safe bundle of real abilities you hand to a workbook. Here, a toolkit can also bring its own piece of interface and hang it in the dock, themed to match everything around it.

The consequence is strange and wonderful: the way you add a feature to the Browser is to write a toolkit. An agent — Claude Code, say — can pick an icon, write a small toolkit, and a new panel simply appears in the top-right corner of your app. No app store, no update, no waiting for the makers. The application grows a new limb because you (or the agent working with you) decided it should.

This is what people mean when they say the Browser is extensible to its core. Most apps offer “extensions” as a fenced-off sandbox bolted onto a frozen core. Here the core and the extensions are the same kind of thing, mounted in the same dock, drawn with the same theme.

The browser SDK: handing the controls to a toolkit

For the dock to be more than decoration, a panel needs to actually do browser things — open a tab, drop a bookmark, read what’s in the viewer, react when you switch documents. The browser SDK is the small set of controls the Browser hands to its toolkits: tabs, bookmarks, viewer state, events.

So a toolkit isn’t just painting a panel; it can drive the surface it lives in. A research toolkit can open three tabs and arrange them. A reading toolkit can watch which workbook you’re viewing and follow along. In effect, an agent can build you your own desktop app out of these parts — and because it’s all workbooks and toolkits, it’s the same craft you’ve already learned, pointed at the app itself.

Waldo: the agent that lives in the app

Because everything taught earlier about agents is true here too, the Browser comes with one already living inside it — a resident agent (named Waldo) that you can talk to about the thing in front of you. It’s not a separate chatbot in a corner; it’s wired into the same dock, the same SDK, the same engine connection. It can open things, weave things, file work for itself when it notices something that should change. The agent and the app are not two products glued together. The agent is just another thing mounted in the same surface — the most active resident of a building made of workbooks.

How you get it

The Browser ships with the command-line tool. There’s no separate download dance, no in-app setup wizard to click through. The one command you already met installs and opens it: the CLI owns setup, the Browser owns the work. And because an agent can drive the whole surface through the SDK, an assistant can install it, open it, and start arranging it for you — set your theme, lay out your panels, pick your starting tabs — before you’ve touched the keyboard.

Why this is the last turn

It’s fitting that this comes near the end of the path, because it only lands once everything before it is in place. A workbook is one file. It speaks one plain language. It gets abilities through toolkits. It comes alive on an engine. Agents work inside it. Plans run themselves.

Take all of that and point it at the application itself, and you get the final, almost recursive idea: the tool you use to build with workbooks is built out of workbooks. There is no privileged layer, no frozen core you’re forbidden to touch. The front door is made of the same material as every room behind it — which means the moment you understand a workbook, you already understand the thing you’re using to hold one.
