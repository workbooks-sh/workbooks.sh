The one command you type

Here is a small mercy you’ve probably stopped expecting from software: there is exactly one tool to learn.

Not a toolbelt. Not a scaffolder and a builder and a deploy script and a signing wrapper and a daemon’s client, each with its own flags and its own config file and its own way of being slightly out of date. Most ecosystems hand you that pile and call it a starter kit, and you spend your first week not learning the work but negotiating with the tools — which one to run before which other one, which flag the build tool grew last month that the deploy tool hasn’t heard about yet, which thing to type when the thing won’t start.

Workbooks makes a different bet. If a workbook is one artifact, and the way you describe it is one grammar, then the way you drive it ought to be one tool. So there is one. It’s called wbx, and the genuinely surprising part of this lesson is how little of it you need to hold in your head.

one handle on the whole thing

The honest way to describe wbx is that it’s a handle, not a brain. It’s a single program that authors, builds, signs, ships, and runs workbooks — but it owns almost none of the cleverness itself. It parses what you asked for, does the light local work directly, and hands everything heavy to the system behind it. The intelligence lives in the ecosystem; the command is the grip you hold it by.

That’s why you won’t need it to understand most of the rest of this Learning Center. The deep ideas — what a workbook is, what an agent does inside one, how a plan compiles, how provenance travels — live in the artifact and the system, not in the tool. wbx is the consistent way you reach all of them. Learn the handle once; it works the same on every door.

There are around thirty things it can do, which sounds like a lot until you notice they fall into a few plain families: one for authoring (starting a workbook, previewing it live, shaping its contents), one for making (turning your work into one finished file), one for trust (signing a file so its origin travels with it), one for the parts you add (toolkits, workflows, agents), one for the engine when you want a workbook to keep living on a server, and a handful of everyday ones that just look after you and the tool itself.

You don’t memorize the thirty. You learn that the families share the same manners — you start a thing, you check a thing, you do a thing — and once you’ve used one family, you’ve basically used them all. Better still, every time a command succeeds, it tells you the command you probably want next. The tool teaches its own shape as you go, so the manual is something you almost never have to open.

the gentlest possible tool

Most command-line tools treat a missing answer as your fault. You forgot a flag; here’s an error; go read the docs. wbx was built on the opposite instinct — that a learning curve is a bug, and the tool, not the human, should be doing the work.

So when you leave out something with an obvious answer, it picks the obvious answer and tells you what it picked. When the choice is genuinely yours, it offers a tiny menu rather than a wall of text. Type the command with nothing after it and, instead of scolding you, it answers the only question a newcomer actually has — where am I, and what can I do next — telling you which version you’re running, whether the engine is reachable, and the moves available from here.

There’s even a command whose whole job is to check that everything is set up correctly, and it’s deliberately the gentlest one of all. It runs a few honest probes (is the tool installed where it should be, is anything listening, are you standing in a workbook), reports what it finds in plain language, and — the quietly radical part — it never fails because it found a problem. A health check that found something wrong still did its job. It reports; it doesn’t judge. Every unwelcome finding comes with the literal next command that fixes it, not a generic “see documentation.”

That posture runs through the whole tool — the difference between software that makes you prove yourself worthy of it and software that’s just trying to help you get where you’re going.

two minutes to your first one

Here’s the entire shape of getting started, and notice what isn’t in it: no account, no server, no setup ceremony. You install the one tool, and that’s the whole prerequisite.

You ask the tool to start a new workbook, and it makes you a folder with a single source file inside. You ask it to preview that workbook live, and it opens a page in your browser that reloads every time you save — source on one side, the living page on the other, following along as you type. That loop is the authoring experience: edit, save, watch it change.

When the thing is worth keeping, you ask the tool to bundle it, and it packs everything — the page, its source, its data — into one self-contained file you can mail like an attachment. Ask it to sign that file, and it stamps your origin into the artifact so anyone receiving it can prove where it came from.

No server was involved in any of that. The engine only enters the story later, when you want a workbook to keep running after you close your laptop — and even then, standing one up is one more command. The everyday work of making something lives on your own machine, in plain files, with one tool.

the same tool the agents use

Now the part that elevates wbx from a convenience into something closer to a principle. The tool knows it has two kinds of users, and it changes its manners for each without changing what it does. When you are at a terminal, it’s warm and helpful — picking defaults, offering menus, suggesting the next step. The moment its output is being read by a program instead of a person — piped into a script, or driven by an AI agent — it quietly drops the friendliness: no menus to hang on, no colors a log can’t read, just clean, predictable output a machine can trust. Same work underneath; only the manners change, decided once, at the very end.

This matters more than it sounds. The usual industry answer is two separate things — a tool for humans and an interface for machines — and they always drift apart, until the two quietly disagree about what the software even does. wbx refuses that fork: one program with good manners, not two programs that fall out of sync.

And it goes further than most people expect. The very same tool runs inside the system, in the sandbox where Workbooks’ own AI agents do their work. So when an agent’s log says it ran a particular command, you can run the identical command on your own machine and see the identical thing. There’s no translation layer between what an agent does and what you’d do — no secret interface the machines use that you can’t.

That’s what makes “people and AI build together” more than a slogan. It has to be true at the level of the tool itself, or it isn’t true anywhere. When you and the agent reach for the exact same handle, with the same words and the same behavior, you’re genuinely working in the same place — not watching a machine operate controls you can’t touch.

So that’s the whole of it. One tool, a few families with shared manners, gentle with humans and trustworthy with machines, the same on your laptop and inside the engine. You learn the handle once — and everything else in this Learning Center is what’s on the other side of the door it opens.
