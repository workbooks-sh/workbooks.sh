#+TITLE: Engine spike (wb-hhf.2): runtime OCI image -> raw ext4 -> Virtualization.framework VM
#+DATE: 2026-06-10

Prove the desktop .app can boot =ghcr.io/workbooks-sh/runtime:latest= from a
raw ext4 disk in a Virtualization.framework VM on Apple Silicon / macOS 15 —
no docker, no podman, no krunvm.

* Verdict

*PROVEN, via vfkit.* Cold boot (VM launch -> HTTP 200 from the runtime over
the VM boundary): *0–2 s* across 5 runs. The full desktop seam works:

- raw ext4 disk built on macOS from the OCI image (skopeo + umoci + mke2fs)
- vfkit direct-kernel boot (Alpine =-virt= kernel + netboot initramfs + addon)
- guest DHCPs on vfkit NAT (=192.168.64.x=), host curls guest IP directly
- =GET /.well-known/workbooks-runtime= -> 200 (public discovery, no token)
- =/disco/runtime.json= (with bearer token) lands on the HOST via a
  virtio-fs share -> host reads token -> =GET /health= with bearer -> 200

krunkit is a *dead end* for this shape: libkrun-efi only EFI-boots a disk, a
raw ext4 filesystem has no ESP/bootloader, and krunkit 1.2.1 has no
--kernel/--initrd flags. 45 s, zero console output. It would need a GPT disk
with ESP + arm64 bootloader baked in (podman-machine style) — defeats "simple
raw ext4". vfkit's direct-kernel path is strictly simpler.

* Scripts

| build-disk.sh   | OCI -> rootfs -> init injection -> ext4 disk + kernel + initramfs |
| boot-vfkit.sh   | boot, find guest IP, prove HTTP + virtio-fs discovery; =--keep= to leave running |
| boot-krunkit.sh | the recorded dead end |

The rootfs-prep recipe was PROMOTED to =../engine-disk/lib.sh= (one source of
truth) — build-disk.sh sources it; Linux CI (=engine-disk/build-ci.sh=, via
=.github/workflows/engine-disk.yml=) runs the same functions and publishes
=ghcr.io/workbooks-sh/engine-disk= for the desktop's vfkit lane (machine.rs).

#+begin_src sh
HOMEBREW_NO_AUTO_UPDATE=1 brew install skopeo umoci e2fsprogs vfkit
./build-disk.sh        # ~75 s first run (network), ~7 s warm (mke2fs only)
./boot-vfkit.sh        # SUCCESS: HTTP 200 ... in 2s

Work dir =/tmp/wb-spike= (override =WORK=). Spike uses guest-IP curl; host
port 4000 (prod docker runtime) is never touched.

* Timings (M-series, macOS 15.6)

| skopeo pull (network)                | ~63 s        |
| umoci unpack                         | ~15 s        |
| mke2fs -d (1.2 G rootfs -> 3 G img)  | ~5 s         |
| VM launch -> guest IP via dhcpd_leases | 0–1 s      |
| VM launch -> HTTP 200 from runtime   | *0–2 s* (n=5) |

Kernel-side: ext4 root mounted at +0.18 s, BEAM up and discovery written at
~+1 s. The Erlang release itself is most of the boot.

* How the disk boots

- *Kernel*: Alpine =netboot/vmlinuz-virt= (aarch64). It's an EFI-zboot PE
  (="MZ..zimg"=) wrapping a gzip'd Image; VZLinuxBootLoader requires the
  UNCOMPRESSED Image, so build-disk.sh parses the zimg header (payload
  offset/size at bytes 8/12) and unwraps. 35 MB raw (10 MB gzipped).
- *Initramfs*: Alpine =netboot/initramfs-virt= + an appended cpio.gz addon:
  - ext4/jbd2/mbcache/crc16 =.ko= taken from the matching =linux-virt= apk
    (the netboot initramfs has NO ext4 — it lives in the modloop).
  - =/init= shadowed by a wrapper that =busybox insmod='s (in order):
    crc16, mbcache, jbd2, ext4, af_packet, failover, net_failover,
    virtio_net, fuse, virtiofs — then execs the original alpine init
    (shipped as =/init.alpine=). cmdline: =root=/dev/vda rw rootfstype=ext4
    modules=ext4 init=/sbin/wb-init console=hvc0=.
- *Disk*: =mke2fs -t ext4 -d rootfs disk.img 3G= straight from the umoci
  rootfs — no loop mounts, works fully unprivileged on macOS.
- *PID 1 in rootfs*: =/sbin/wb-init= (injected) mounts proc/sys/dev{,pts},
  remounts =/= rw, tmpfs =/run= =/dev/shm=, mounts the =disco= virtio-fs tag
  on =/disco=, brings up lo + eth0, =udhcpc= against vfkit NAT, exports
  =WB_WEB=1 PORT=4000 WB_DESKTOP=1 WB_DESKTOP_DIR=/disco WB_DATA=/data
  WB_EMBED=local=, then =exec bin/workbooks start= (BEAM as PID 1 — fine).

* Gotchas (each one cost a boot)

1. brew skopeo ships a v1 =registries.conf= it itself rejects -> pass
   =--registries-conf= with a one-line v2 file.
2. Alpine vmlinuz is EFI-zboot -> unwrap or VZ refuses ("compressed file").
3. In the alpine initramfs =/lib= and =/bin= are symlinks -> =usr/*=. The
   kernel cpio unpacker REPLACES a symlink with a directory entry, orphaning
   the musl loader -> "/init error -2" panic. Stage addon files under
   =usr/lib/...=.
4. The initramfs =modprobe= is kmod and consults only =modules.dep.bin=
   (binary index, can't regenerate on macOS) -> text =modules.dep= edits are
   ignored; load addon modules by path with insmod from a shadowed =/init=.
5. busybox dispatches applets on argv[0]; a binary named =wb-busybox= yields
   "applet not found" for everything. Name it =busybox=.
6. alpine init mounts root RO even with =rw= in cmdline -> remount in wb-init.
7. =af_packet= + =virtio_net= only get loaded on alpine's =ip=dhcp= netboot
   path; without them udhcpc dies (=AF_PACKET ... not supported=) and the
   BEAM exits 1 ("Protocol 'inet_tcp': ... enetunreach" — kill-init panic).
8. Debian's util-linux =mount -t virtiofs= fails ("must be superuser", even
   as real root); busybox mount works.
9. macOS =/var/db/dhcpd_leases= strips leading zeros from MAC octets — pick
   a MAC with none (=5a:94:ef:e4:1c:ee=) or normalize when matching.
10. vfkit NAT DHCP is macOS bootpd; lease shows up within ~1 s of boot.

* What bundling in the .app needs

| binary / asset            | size            | note                                          |
|---------------------------+-----------------+-----------------------------------------------|
| vfkit                     | 30 MB           | Apache-2.0; or link Virtualization.framework directly from the app later |
| kernel-image              | 35 MB (10 MB gz) | unwrap zboot at install time                  |
| initramfs-wb              | 9.5 MB          | build once per kernel bump, ship as asset     |
| disk.img                  | 1.2 GB used / 3 GB sparse | per runtime release                  |
| busybox.static            | 1.1 MB          | baked into the disk                           |

- *Entitlement*: the process that launches the VM needs
  =com.apple.security.virtualization= (vfkit's brew signature has it; our
  signed/notarized .app must carry it too). NAT networking needs nothing
  beyond that (no =com.apple.vm.networking= approval required).
- *Disk delivery*: building the disk on-device needs skopeo+umoci+mke2fs
  (~heavy, GPL bits). Recommend instead: CI builds =disk.img.zst= +
  kernel + initramfs as a release artifact next to the runtime image
  (Linux CI can do it trivially), .app downloads on first run / engine
  update. Disk stays immutable per release.
- *User data*: keep =/data= OFF the rootfs disk — second virtio-blk data
  disk (or a virtio-fs share) so engine updates are "swap disk.img".
- *Discovery*: virtio-fs share of an app-support dir as =/disco= is proven —
  the app reads =runtime.json= (bearer token) exactly like the docker flow.
- *Localhost port*: spike used guest-IP curl. For =127.0.0.1:41xx= either
  run a trivial TCP proxy in the app (it knows the guest IP from
  dhcpd_leases) or move to gvproxy/=virtio-net,unixSocketPath= later.
- *Lifecycle*: vfkit =--restful-uri tcp://127.0.0.1:4199= gives state/stop
  REST control; SIGTERM to vfkit also kills the VM cleanly.
