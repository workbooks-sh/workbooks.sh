* What this doc is

  The single source of truth for the toolkit system *in the clean-room runtime*
  (this repo, workbooks.sh). It reconciles the restored mainline design docs
  (TOOLKITS-PLAN / TOOLKIT-SKILLS-V2 / TOOLKIT-DISCOVERY — kept for provenance,
  each banner-flagged) with what the clean-room actually is: a ~2.4k-LOC L0 core
  where a CLI is a WASM `run-command`, not a native PATH binary, and where
  telemetry + SQLite/VFS are first-class.

  Read ARCHITECTURE.org for the onion (L0–L4); a toolkit is L4. Read
  TOOLKIT-MANIFEST.org for the unified `#+EXEC` manifest spec (epic wb-rhs).

  UNIFICATION (2026-06-08, wb-rhs): "extension" is no longer a separate noun.
  A 3rd-party untrusted WASM component is just a *toolkit* at `#+EXEC: component`
  with `#+TRUST: third-party`. One package, one build, one trust model, one
  registry, one discovery query `(tags :toolkit:)`. EXTENSIONS-ORB.org is
  SUPERSEDED; its architecture survives, its "keep two words" call is reversed.

* The three nouns (settled — do not conflate)

  - *Capability* — a Dock import (a host power: vfs, llm, net, browse), gated by
    Policy. The thing WASM cannot do that the host provides.
  - *Command* — the stdio executable leaf: a CLI converted to a runnable WASM
    module (argv+stdin→stdout), invoked by name via the `run-command` Dock
    import. CommandRegistry. jq, grep live here. (A command is one *shape* a
    toolkit's artifact takes — `#+EXEC: command`; see the EXEC set below.)
  - *Toolkit* — the unit you author, build, and share. A `:toolkit:`-tagged org
    node (manifest) + a SKILL_DIR of progressive-disclosure recipes, plus the
    WASM artifact(s) it builds. The manifest's `#+EXEC` field selects HOW the
    artifact is invoked (command / component / kernel / task / federation) and
    `#+TRUST` selects the consent posture (first-party / third-party). Discovered
    by `(tags :toolkit:)`. NOT trusted by virtue of being on disk — see
    "Security model". (The earlier "Trusted" label was a trust-model defect: the
    discovery root is an unauthenticated writable directory; read-only surfaces
    are open, execution is default-deny + sandboxed.)

  Consumers (a toolkit serves all four, by EXEC shape): the *agent* reads skills
  and calls a `command` via bash; a *workflow* orchestrates; another *component*
  calls via `run-command` / a WIT import; the *fabric* invokes a `kernel` in a
  hot loop (the media/render class). A toolkit is NEVER a new core registry
  entry — bash/the Dock stays the agent's one tool.

* The core decisions

** Execution mode is per-toolkit, declared in the manifest (NOT a global rule)
   A toolkit's manifest declares how its CLI runs. No single "everything is
   WASM" or "everything is PATH" law — resolve case-by-case as we re-author.

   #+BEGIN_SRC org
   #+EXEC: command       # argv+stdin→stdout WASM run-command (jq, grep) — default, most portable
   #+EXEC: posix         # native PATH binary, run under the `posix` Policy profile inside the deploy container (ffmpeg-class)
   #+EXEC: task          # no single CLI; the toolkit ships :role task bash recipes run via `wb toolkit run`
   #+EXEC: federation    # no CLI; a data-source plugin + sync daemon (see §Federation)
   #+EXEC: component     # WIT-typed component on engine.wit; typed I/O, in-process call (absorbs the old "extension")
   #+EXEC: kernel        # bytes→bytes hot loop, instantiate-once-call-many; the fabric/media-render class (wb-rhs.5)
   #+END_SRC

   Orthogonal to EXEC, the manifest declares trust posture:
   #+BEGIN_SRC org
   #+TRUST: first-party  # yours; default profile, no extra consent (default)
   #+TRUST: third-party  # untrusted supply chain; deployer must review + grant #+CAPS (the old "extension" consent point)
   #+END_SRC
   See TOOLKIT-MANIFEST.org for the full field list and per-shape requirements.

   DEPLOYMENT NOTE (corrected 2026-06-07): we are NOT using microVMs. The whole
   runtime is wrapped in ONE portable Linux container (OCI/Docker) for deployment
   isolation — local now (instead of seatbelt), same image in cloud. It is not
   per-component and not a Firecracker/libkrun microVM. That single deploy
   container is the OS-isolation boundary, so `posix` native binaries are safe
   there; `command` (WASM) is the tighter, portable default. `wb toolkit verify`
   checks the declared EXEC mode is satisfiable (command registered / binary on PATH).

** Progressive disclosure is the whole point (carried forward, unchanged)
   Manifest = the INDEX (need-keyed table), skills read on demand via `cat`.
   Three tiers an agent reaches for the HIGHEST that fits:
   1. MANIFEST — auto-injected catalog row (+ #+FLOW for deep CLIs).
   2. TASK — one runnable recipe per common multi-verb NEED (the noun, not a
      verb chain). Default entry for deep CLIs.
   3. LEAF — full per-verb reference, read only off the happy path.
   Thin skill = one .org; thick skill = skills/<slug>/SKILL.org + references/.
   This is all already specified in AUTHORING.org + TOOLKIT-SKILLS-V2.org.

* Minimal authoring: the CLI→WASM auto-wrap (the build model)

  The authoring goal is ZERO glue code per toolkit. The author writes a build
  descriptor (a few manifest lines) + the org skills. Nothing else — no bindings,
  no host shim, no per-CLI API definition.

** The load-bearing insight: stdio IS the universal API
   A CLI's interface is `argv + stdin → stdout + exit code`. Every CLI shares
   that ABI; WASI preserves it exactly. So `run-command(argv, stdin) → stdout` is
   ALREADY the API for every toolkit. There is nothing to generate. You do NOT
   compile a CLI to get a "schema" — you get the universal stdio ABI for free.

   Corollary (state plainly, it prevents a wrong turn): compiling a CLI to WASM
   does NOT and CANNOT yield a *semantic* schema (what the flags/subcommands
   mean, the gotchas, the right recipe). That knowledge is un-extractable from a
   binary — it is exactly what the org skill is. The .wasm and the org are
   orthogonal:
   - .wasm  = AUTO-BUILT from source. stdio ABI universal ⇒ zero glue.
   - skills = HAND-AUTHORED. the semantic surface; un-generatable from a binary.
   (`<cli> --help` captured in the build sandbox MAY seed overview/leaf drafts —
   a starting point, never a substitute for the depth bar.)

** The manifest build descriptor (the few lines an author adds)
   #+BEGIN_SRC org
   #+EXEC:       command            # see EXEC modes above
   #+BUILD_SRC:  cargo:jaq-interpret # crate | git+<url> | path:<dir> | bin:<name>
   #+BUILD_LANG: rust               # rust | go | js | py — picks the build recipe
   #+CAPS:       net                # WASI worlds / Dock imports the wasm may use; deployer grants
   #+END_SRC
   `wb toolkit build <name>` → PackageManager picks the lang recipe → compiles
   under Sandbox (network-denied) → content-addresses → registers the artifact in
   CommandRegistry under CLI_BIN. One single .wasm per toolkit CLI. (Bundling the
   .wasm + org into a distributable .html Workbook is OPTIONAL — a distribution
   concern, not an authoring one.)

** Per-language build recipes (extends PackageManager.build_dir/2)
   | Lang   | Path                                            | Reality                       |
   |--------+-------------------------------------------------+-------------------------------|
   | rust   | cargo build --target wasm32-wasip2 + component  | cleanest; jq/grep already this |
   | go     | GOOS=wasip1 go build / TinyGo                    | works for many                |
   | js/ts  | Javy / jco componentize                         | works                         |
   | py/rb  | componentize-py                                 | heavy; pure-source only       |
   | c/c++  | wasi-sdk clang                                   | hard/often infeasible → posix |

   HONEST SCOPE: auto-wrap works for CLIs that compile CLEAN to WASI — pure
   compute + stdio + files (~80%: text tools, jq-likes, image libs). Native C
   deps / threads / browser / GPU (ffmpeg-class) do NOT transparently wasm — they
   take #+EXEC: posix. Do not promise "any CLI"; promise "any WASI-clean CLI,
   posix-fallback the rest."

* Capabilities: what WASM can't do — two layers, do not conflate

  "Outsource to the build profile that does the dock pallet assembly" is really
  TWO things:
  1. BUILD-TIME (the build recipe) — compile the crate to wasm + link as a
     component, under Sandbox. PackageManager + Sandbox. Produces the .wasm.
  2. RUN-TIME (the Dock) — when the running wasm tries what WASM can't, it calls
     OUT to a host import, gated by Policy. "Dock pallet assembly" =
     Instance.Imports.for_caps/3 building the host closures for the granted caps.
     THIS ALREADY EXISTS.

  The capability ladder (free → escape hatch):
  | CLI needs                       | Mechanism                                          | Cost            |
  |---------------------------------+----------------------------------------------------+-----------------|
  | compute, stdin/stdout           | the run-command ABI                                | free, today     |
  | clock/random/env/scoped dir     | WASI-p2 (host configures preopens)                 | cheap           |
  | network                         | wasi:http outbound, gated by `net` cap (stock CLIs)| REAL WORK       |
  | TLS-fingerprint / headless browser | custom Dock import (browse-fetch); CLI never holds a socket | per-cap closure |
  | ffmpeg-class native             | #+EXEC: posix, native in the deploy container      | accept it       |

  The one genuinely new decision: support `wasi:http` host-gated so a STOCK
  network CLI runs unmodified (gated at the WASI boundary), rather than forcing
  CLIs to call our typed net-fetch (only works for CLIs written for us — not
  stock). Recommendation: wire wasi:http behind the `net` cap; raw TCP
  (wasi:sockets) behind a stricter cap. The capability gate stays the single
  telemetry/enforcement chokepoint (per EXTENSIONS-ORB.org).

** The FS bridge — preopen ↔ VFS (widens auto-wrap to file CLIs)
   Three FS layers stack: the deploy container's Linux FS (outer), WASI's preopen FS (the
   wasm-level capability FS — deny-by-default, grant-per-dir), and our SQLite VFS
   (vfs.ex volumes workspace/memory/tmp). The CONNECTOR is the preopen:
   `wasmtime --dir <host>::<guest>` mounts a host dir into the guest. Back that
   host dir with a VFS volume and a STOCK file-CLI operates on our VFS
   transparently. v1 = materialize volume → temp dir → preopen → run → copy
   changes back; v2 = a virtual FS over SQLite. PackageManager.run/3 already
   takes `dirs` (the preopen list); wiring it to a VFS volume is the next step.
   PROVEN 2026-06-07 (see §SPIKE): a normal read+write CLI round-tripped through
   a host::guest mapping; without the mapping the guest saw nothing (NotFound) —
   container-style isolation, function-granular.
   mmap is NOT a wall — it is EMULATABLE at the build layer (PROVEN 2026-06-07).
   You cannot forward the raw memory accesses to the host (they are loads/stores,
   not calls), but you do not need to: give the guest its OWN mmap implemented over
   pread/pwrite (the WASI file ops that DO route). A ~30-line shim
   (malloc+pread for MAP_PRIVATE read; flush-on-msync/munmap for MAP_SHARED) was
   compiled with `zig cc prog.c mmap_shim.c` and ran end-to-end: read-through-
   pointer AND write-back-through-pointer to the host file, both correct.
   - Delivery = a BUILD-PROFILE concern (the crate/sysroot pallet). C/wasi-sdk
     CLIs link the shim → mmap() resolves to the emulation, CLI unmodified.
     WIRED (P10, 2026-06-07): build/shims/mmap_shim.c (file-backed mmap over
     pread/pwrite — MAP_PRIVATE via malloc+pread, MAP_SHARED flush on
     msync/munmap via pwrite) is linked into EVERY C/wasi build by
     PackageManager (build_c inline blocks + build_dir(_, "c")). wasi-libc now
     ships its own mmap that just returns ENOSYS, so a plain duplicate collides;
     we redirect mmap/munmap/msync to the shim's __wrap_* with `wasm-ld --wrap`.
     zig 0.16's cc front end rejects --wrap, so PackageManager two-phases it:
     compile sources+shim to objects, capture the exact `wasm-ld` link line from
     `zig cc -v` (its sysroot/libc paths live in zig's cache — never hardcoded,
     stays correct across zig versions), then replay that line through wasm-ld
     with --wrap injected. Proof = build_recipes_test.exs "build_dir C fixture:
     mmap shim round-trips a file": a C CLI mmaps MAP_SHARED, reads through the
     pointer ("read-through: h") and write-backs ("hello world\n" → "HELLO
     WORLD\n") through the host file via a wasmtime preopen. CLI source untouched.
     Rust crates that hard-gate on cfg(target_arch) (memmap2 returns Unsupported
     before calling mmap) need a [patch.crates-io] override/fork, OR normal IO.
     The Rust path (memmap2): unlike C, the shim cannot be link-injected because
     memmap2's wasm cfg returns Err(Unsupported) in Rust BEFORE any mmap() FFI
     call is emitted — there is no symbol to --wrap. Override the crate at the
     workspace root:
       #+begin_src toml
       # Cargo.toml
       [patch.crates-io]
       memmap2 = { git = "https://github.com/<org>/memmap2-wasi", branch = "wasi-pread" }
       #+end_src
     The fork's only delta is the wasm32-wasi Mmap::map/map_mut impl: instead of
     returning Unsupported, declare `extern "C" { fn mmap(...); }` and call it,
     so it links the SAME C shim (build it into the crate via a build.rs
     `cc::Build::new().file(".../mmap_shim.c")` + the --wrap flags). Net: one C
     shim, two front doors — C/zig links it directly; Rust reaches it through a
     patched memmap2 whose wasm impl FFIs into mmap() rather than bailing. Crates
     that just use std::fs / normal IO (the majority of file-CLIs) need neither.
   - Residual TRUE limits (rare for CLIs, → #+EXEC: posix only here): no lazy
     demand-paging (whole region eager-loaded → files near/over wasm32 ~4GB don't
     fit; memory64 raises the ceiling), and cross-process shared-memory IPC
     (separate sandboxes share no address space — cannot be faithfully emulated).
   So the posix-fallback set shrinks from "anything using mmap" to "huge-file mmap
   + shared-memory IPC" — which toolkit CLIs do not do. sd specifically still needs
   a memmap2 patch (hard-gated) or posix; most file-CLIs work with the shim.

** Network → a `browse-fetch` Dock import bound to Workbooks.Browse  [DECISION: Route B, 2026-06-07]
   DECIDED: use the Dock-import route only — safest, reuses what we have, no new
   library. Do NOT enable wasi:sockets/wasi:http or `-S inherit-network` unless a
   future need proves the existing Browse/HTTP stack can't serve it.

   Add `browse-fetch` (and as needed `net-fetch`) as a Dock import bound to
   `Workbooks.Browse.fetch`, gated by the `browse`/`net` Policy cap — exactly the
   shape of the existing vfs-query / run-command / llm-complete imports
   (instance/imports.ex). The guest calls the import; the host performs the fetch
   with the full browser stack (native/Exa/Firecrawl + proxy, TLS handling); the
   guest NEVER holds a socket. The capability gate stays the single
   enforcement/telemetry chokepoint, and the host owns all credentials/egress
   policy. Cost: the CLI must call our import (an adapted CLI or a component) —
   acceptable; we are not chasing transparent stock raw-socket CLIs.

   REJECTED for now — Route A (wasi:http / wasi:sockets / inherit-network):
   wasmtime 45 supports `-S http/tcp/udp/inherit-network`, but it widens the egress
   surface and would route around our Browse policies. Park it; revisit only if a
   library/capability gap appears that HTTP-via-Browse genuinely can't cover.

* SPIKE — empirical proof (2026-06-07, this box)

  Tested the auto-wrap claim end-to-end on a REAL upstream CLI we did not write:
  `sd` (a sed-alternative). Verdict: the common case SPIKES; the capability edge
  SMOKES exactly where the model predicts. Toolchain present: wasmtime 45.0.1,
  rustc 1.94 + wasm32-wasip1, wasm-tools, tinygo/go, mix (OTP 28).

  Build (ZERO edits, plain cargo — the whole "auto-wrap build step"):
  #+begin_src bash
  cargo install sd --target wasm32-wasip1 --root /tmp/spike-sd --no-track
  # → /tmp/spike-sd/bin/sd.wasm  (1.5 MB, built in 10.7s, first try)
  #+end_src
  It compiled clean even pulling in rayon (threads) + memmap2 — they degrade
  rather than break the build.

  Ran through the PRODUCTION runtime modules (mix run --no-start):
  | What                                   | Path                          | Result        |
  |----------------------------------------+-------------------------------+---------------|
  | sd 'wasm' 'WASM' over stdin            | PackageManager.run/3 (argv)   | ✅ correct     |
  | sd '[0-9]+' '#' (regex engine in wasm) | PackageManager.run/3          | ✅ correct     |
  | sd --help (clap argv parsing)          | wasmtime                      | ✅ correct     |
  | jq filter (existing command)           | CommandRegistry.run/2         | ✅ still works |
  | sd file-edit mode (memmap2 mmap)       | wasmtime --dir … (preopen)    | ✅ SMOKES: "unsupported" |

  Findings carried into the plan:
  1. *Auto-wrap is real* for WASI-clean compute+stdio CLIs — zero glue, the stdio
     ABI IS the API, confirmed against an untouched third-party binary.
  2. *The boundary is exactly where predicted*: sd's mmap file-mode fails even
     WITH a preopen ("unsupported") — that path needs #+EXEC: posix. Stdin-filter
     mode is the sweet spot.
  3. *GAP the spike exposed*: the implemented run path was stdin-ONLY (run/2,
     `wasmtime <wasm> < file`) — no argv. Real CLIs need argv. Added
     PackageManager.run/3 (argv + optional preopen dirs, shell-escaped, no
     injection) this commit. The run-command Dock import + CommandRegistry still
     need the argv parameter threaded through — that is now explicit P4 work.
  4. *Derived-artifact rule honored*: sd.wasm is NOT committed (it is rebuildable
     from the one cargo line above), per ARCHITECTURE.org "WASM owns the artifact,
     Org owns the spec."

  Reimplement the archive's Rust toolkit.rs (2278 LOC) as Elixir subcommands in

  underlying CLI from our skill files." It is mostly thin `cat`/`ls` over org +

* Integration with the new systems (the real gaps)

** Telemetry — every toolkit-CLI call should be a step
   Today `run-command` (instance/imports.ex) has no telemetry hook and no
   workdir context, so a toolkit call emits nothing to `_steps.jsonl`. Plan:
   - Thread workdir/tenant into the `run-command` closure.
   - On each call, append a step `{tool: "toolkit:<id>", exit_code, dur_ms, ts}`
     to `_steps.jsonl` (same shape agent.ex/log_step already writes; surfaced by
     workflow/telemetry.ex summary/1).
   - The capability gate is the chokepoint (per EXTENSIONS-ORB.org) — wiring the
     hook here makes toolkit usage observable by construction.

** SQLite / VFS / secrets — give commands a Dock
   Commands currently run via bare `wasmtime` with NO Dock (package_manager.run/2)
   → they can't read VFS, secrets, or net. Plan: route capability-needing
   commands through the Instance Dock (vfs-query, net-fetch, the secret model)
   gated by the toolkit's declared caps, instead of the context-free wasmtime
   path. Honor the skill's `:NETWORK:` / `:DESTRUCTIVE:` drawer flags at call
   time (skip offline / confirm before running).

* Federation (SaaS connectors) — the three-face toolkit

  For Notion/GitHub/Stripe/Linear-style integrations (see PLUGINS-PLAN.org;
  linear/ + asana/ already shaped this way). A federation toolkit has three faces
  in one directory:
  1. *Base* — manifest.org + skills/ — how the agent uses it.
  2. *Data-source* — plugin/manifest.org (#+SLOT: data-source, #+ENTITIES,
     #+IMPL) — the OQL read face (`SELECT … FROM linear-issue`).
  3. *Sync daemon* — sync.org (:daemon: node, interval pull) — mirrors the API
     into `:task:`/entity nodes; supervised, airgapped from the agent.
  Auth is centralized (Plugin.Auth.fetch context-aware: env → keychain → broker),
  declared via #+ENV_KEYS, never in toolkit source.

* Security model (wb-sec — hardening, 2026-06-07)

  The discovery root ($WB_TOOLKITS_ROOT or ./toolkits) is an UNAUTHENTICATED,
  writable directory. A toolkit there is UNTRUSTED supply-chain input — its
  location does not make it first-party. The hardening enforces:

  ** Trust boundary (toolkits.ex)
     - READ-ONLY surfaces (list/show/search) stay open, but: skill slugs are
       path-contained (reject `..`/separators; canonicalize + assert containment
       under <toolkit>/skills/), and $WB_TOOLKITS_ROOT is honored only if it is
       an existing dir (a blank/bogus value can't repoint the surface).
     - EXECUTION surfaces (`verify` pre blocks, `run` task blocks) are
       DEFAULT-DENY. A :role bash block is arbitrary host code; it runs ONLY when
       the operator opts in via WB_TOOLKIT_EXEC=1, and then under
       Workbooks.Sandbox (network-denied, fs-confined) with a wall-clock cap and
       a `ulimit` prologue (anti fork-bomb) — never bare host bash.
     - BUILD refuses a CLI_BIN that collides with a reserved built-in
       (jq/grep/upper) before any compile.

  ** Build isolation (package_manager.ex / sandbox.ex) — NOW WIRED
     Every compiler invocation (cargo build, tinygo, zig cc, wasm-ld, javy, bun
     build, inline rust) runs through `Workbooks.Sandbox.run` (network-DENIED,
     fs-confined), and offline (`cargo build --offline`). The doc previously
     claimed sandboxed builds while the code shelled out to the host directly;
     that gap is closed. RESIDUAL RISK: `cargo install <crate>` (the crate:
     auto-wrap) MUST fetch from the registry, so it runs FS-confined but
     network-PERMITTED (`Sandbox.run_net`); a fetched crate's build.rs/proc-macros
     still execute with network during install — installing an arbitrary published
     crate is an inherent trust decision (allowlist/review crate names). The
     offline, fully network-denied path is the local path: source dir.

  ** Command registry (command_registry.ex)
     - Built-ins (jq/grep/upper) are RESERVED and cannot be shadowed; registry/0
       merges built-ins last so even a poisoned dynamic term loses at lookup.
     - register/3 rejects empty/nil/malformed names and any wasm path outside the
       content-addressed build/commands/ store.
     - cargo install gets `--` before the crate spec and a charset check on the
       crate token (kills option-injection like --git=<url>).
     - Content-addressed artifacts are re-verified (sha256 == filename) at RUN
       time, closing the register→run TOCTOU.
     - The run-command path enforces input/argv size caps and runs wasmtime under
       `-W timeout`/`-W fuel` (the Policy CPU cap previously never wrapped it).
     RESIDUAL RISK: the dynamic registry is still a single process-wide
     :persistent_term (finding #9) — registration is now name/path-guarded and
     size-bounded, but it is not yet per-Instance/per-tenant namespaced, and
     registration is not gated by a Policy capability. Cross-tenant poisoning of
     *non-reserved* command names by code that can call register/3 remains
     possible; full isolation needs a per-session registry struct threaded
     through run/ (tracked as a follow-up refactor).

  ** WASI capability gating (instance.ex / policy.ex)
     - allow_http is DERIVED from the profile (`Policy.allow_http?/1`): only
       `net`/`browse` profiles get it. In stock wasmex that one flag gates BOTH
       the wasi:http import AND store.rs `inherit_network()`+DNS, so `minimal`
       now gets NO host network at all (closing the critical egress bypass where
       every Instance reached wasi:http regardless of caps).
     RESIDUAL RISK (findings #7 tail, #8): stock wasmex `add_to_linker_sync`
     still links the full wasi:p2 *type* surface (clocks/random/filesystem-types/
     cli-environment) into every component unconditionally. wall-clock + CSPRNG
     are therefore still ambient on `minimal`. Removing them requires a custom
     per-profile linker / restricted WasiCtx in the wasmex NIF (or an
     import-allowlist validation pass over the component's imports). That NIF-level
     change is NOT done here; the network egress (the exploitable hole) is closed
     via the allow_http gate, which also disables inherit_network. Clocks/random
     are low-harm ambient caps pending the linker refactor.
