* The contract

  An agent's =:TOOLKITS:= property is a whitespace-separated list of
  toolkit names:

  #+BEGIN_SRC org
  * Workhorse                                                  :agent:
    :PROPERTIES:
    :ID:        workhorse
    :TOOLKITS:  wb git wavelet brandnana
    :END:
  #+END_SRC

  Note: =bash= is NOT in =:TOOLKITS:= — bash is /the/ tool the
  agent uses (the single registry entry). Toolkits are the CLIs
  bash invokes. Listing bash here historically was a category
  error and is silently ignored by the parser.

  Each name resolves to a =:toolkit:=-tagged headline anywhere in
  the Context Tree:

  #+BEGIN_SRC org
  * wb — the canonical Workbooks CLI                           :toolkit:
    :PROPERTIES:
    :ID:        wb
    :KIND:      cli
    :BIN:       wb
    :END:

    A Rust binary on the agent's PATH.  Discover subcommands via
    =wb --help=.  Talks to the engine over HTTP/WS for stateful work;
    links OQL crates as a library for query/memory.

    ** Recipes
       - Query memory:           =wb memory recall "<text>"=
       - Spawn a sub-agent:      =wb agent spawn workhorse "<task>"=
       - Show session:           =wb session show <id>=
  #+END_SRC

* Why a node, not a registry

  Pre-Context Tree, Workbooks had no formal toolkit schema.  The
  agent prompt declared =:TOOLKITS: wb git= (with bash sometimes
  also listed by mistake) but there was no authoritative source
  for what each name *meant*.  Three rules
  break apart cleanly under Context Tree:

  1. *Substrate uniformity.* Every entity in Workbooks (agents,
     skills, memories, hooks, wizards, plugins) is an org headline.
     A toolkit is one more entity, so it lives in the same tree
     under the same parser.

  2. *Progressive disclosure beats catalog-in-prompt.* Hermes
     bakes its tool catalog into every system prompt; the audit
     measured 10–15 % of context burned on tools the model never
     calls.  A Context Tree agent reads a toolkit body only when
     the task at hand routes to it: =bash cat= on the toolkit
     node's source location.

  3. *Discovery is one OQL query.* No bespoke tool-search /
     tool-describe / tool-call subsystem.  Find a toolkit by ID:

     #+BEGIN_SRC oql
     (tags :toolkit:)
     (property :ID: "wb")
     #+END_SRC

     Or by capability:

     #+BEGIN_SRC oql
     (tags :toolkit:)
     (property :KIND: "cli")
     #+END_SRC

* Required + optional properties

  A =:toolkit:= headline SHOULD carry:

  | Property      | Required | Meaning                                                                  |
  |---------------+----------+--------------------------------------------------------------------------|
  | =:ID:=        | yes      | Whitespace-free slug.  Matches the entry in an agent's =:TOOLKITS:= list. |
  | =:KIND:=      | no       | =cli= (default), =mcp=, =http=, =lib=.                                    |
  | =:BIN:=       | =:KIND: cli= | Executable name on the agent's PATH.                                  |
  | =:ENDPOINT:=  | =:KIND: http= or =mcp= | Address the agent connects to.                              |
  | =:OWNER:=     | no       | Package or org that ships this toolkit.                                  |
  | =:VERSION:=   | no       | Semver string.                                                            |

  The HEADLINE BODY is the recipe — what the agent reads on
  demand.  Subsections (=** Recipes=, =** Examples=, =** Gotchas=)
  are conventional but not enforced.

* Resolution at runtime

  =WorkbooksRuntime.AgentDef.parse/1= today produces a list of
  toolkit *names*.  The resolution step (name → toolkit headline)
  is the agent's own responsibility — discoverable via:

  - Direct =Oql.query=:
    #+BEGIN_SRC elixir
    Oql.query("(and (tags :toolkit:) (property :ID: \"wb\"))")
    #+END_SRC

  - Or, when the bash tool is invoked, the toolkit name in the
    invocation is sufficient — PATH resolution does the work and
    the agent never has to look up the catalog in advance.

  A separate runtime module to "validate that every name in
  =:TOOLKITS:= resolves to a real =:toolkit:= node" is a candidate
  for the oql-lint validation rail (L2.5, wb-0xxu.8); not built
  yet.

* What this displaces

  - No =Workbooks.ToolKit.Catalog= GenServer.  The substrate is the
    catalog.
  - No =:TOOLS:= sidecar property.  =:TOOLS:= on an agent today is
    an optional registry-tool allowlist (rare); it is NOT a list
    of toolkit names.  Don't conflate.
  - No tool catalog block injected into the system prompt.  Agents
    learn toolkits the way humans learn CLIs — by reading
    =--help= or by reading the documentation node when needed.
