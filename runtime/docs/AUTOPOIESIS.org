* The idea

  A system is /autopoietic/ when it maintains and re-produces itself. Our
  runtime should: when an agent hits a wall — "I need a capability that does
  not exist" — the system should be able to /grow that capability itself/,
  not stall and wait for a human.

  The founding case (live, 2026-06-11): the lander agent needed web search.
  The native shell that once let it `curl` a SERP had been removed (no-native-
  exec). With no tool for it, the agent did not file "I am missing a
  capability" — it /mislabeled itself "env-gated"/ and spent ~6 hours auditing
  the same five files into ever-smaller copy nits, shipping nothing. A human
  diagnosed it and wired a `web_search` tool. Autopoiesis closes that loop
  without the human.

* The character: the autopoet

  A singular, persistent /system/ agent — peer to the tenant agents (Waldo on
  the lander, the bit.ml crew), owned by no tenant. One central autopoet
  receives metacognitive issues from ALL tenant agents, works one async
  backlog, and implements them. It is the loop-closer.

* The confinement is the NATURE of the editable surface — not a file list

  The autopoet has FULL power, but only over a /declarative configuration
  layer/: data the engine interprets, hot-reloadable and diffable. It never
  writes or runs native code; it always lives in the WASM / host-brokered
  sandbox. Two layers, one line between them:

  - *HOST = the interpreter + the primitives.* The fixed Elixir engine that
    reads the config and runs WASM, plus the irreducible native-brokered
    powers (http, the keyless Browse search, file/git/llm/image). HUMAN-GATED.
    This is the only "native" part and it does not change at runtime.

  - *The configuration layer = the editable substrate.* Org specs + toolkits +
    skills + agent defs + the tool/capability registry + routing + the
    lifecycle spec. HOT-RELOADABLE, DIFFABLE, AUTOPOET-OWNED. Most of the
    runtime's /behaviour/ already lives here (lifecycle.org, agent.org,
    plan.org boards, crew.org, toolkit manifests) — the engine interprets it.

  The autopoet reshapes behaviour by editing this layer. It can author a whole
  toolkit, rewrite a skill, adjust a def, add a tool to the registry, change a
  route or a lifecycle — extensively, not just knobs — because all of that is
  /data the interpreter reads/, never code it runs.

* The meta-loop (and the migration that grows the autopoet's reach)

  1. A gap *already expressible in config* → the autopoet fills it: writes a
     toolkit (via `toolkit-forge`, to the AUTHORING.org standard), a skill, a
     def change, or a registry entry. Tests it (the artifact's own
     test/specimen). Registers it. Closes the issue. The system gained a
     capability /by itself/.
  2. A gap that needs a *new host primitive* the config layer cannot express →
     the autopoet files a HOST issue into a human-gated lane. A human exposes
     the primitive ONCE. From then on it is in the config layer, and the
     autopoet owns it forever.

  Direction of travel: deliberately *migrate behaviour out of hardcoded Elixir
  into the declarative layer*, so step (2) happens less and the autopoet's
  reach grows. THE TOOL SURFACE is the first target — web_search proved the
  agent tool list should not be hardcoded in `agent.ex`. The host should hold
  PRIMITIVES; a registry (config) should DECLARE which primitives are exposed
  as which tools, composably — so the autopoet can add a tool without a host
  edit.

* The loop in one line

  sense (an agent files a metacognitive issue instead of stalling) → triage
  (the autopoet dedupes/prioritises) → implement (edit the config layer,
  test, register) → close. Host-primitive gaps fork to a human lane.

* Phases

  1. *Issue seam* — `file_issue` agent tool + the system backlog
     (`WB_DATA/autopoet/issues/*.org`). Agents stop stalling; they file.
     (This doc + `Workbooks.Autopoet`.) ← phase 1, here.
  2. *The autopoet character* — its def (system prompt + laws: edits the config
     layer only, toolkit-first, test-before-register, host-needs are gated
     issues). `runtime/priv/autopoet/autopoet.org` — embedded in the BEAM at
     compile time (ships in every release), `WB_AUTOPOET_DEF` overrides.
  3. *The autopoet worker* — a system tenant the runtime supervises, polling
     the backlog on its own cadence. Depends on the multi-tenant keeper.
  4. *Declarative tool/capability registry* — lift the agent tool surface out
     of hardcoded `agent.ex` into config the autopoet can edit (host keeps the
     primitives). The structural migration that makes the loop real.
  5. *Proof* — re-run the web_search scenario AS a toolkit: file "no web
     search," let the autopoet forge a web-search toolkit, watch it land.

* Laws (binding on the autopoet, once it runs)

  - You NEVER write or run native code. Your edits are to the declarative
    layer (org, toolkits, skills, defs, registry, config). The host
    interpreter is not yours to touch.
  - A change must be TESTED before it is registered (the artifact's own test /
    specimen / `wb content check` / a smoke run). An unverified capability is
    not shipped.
  - A gap you cannot fill in config is a HOST issue you FILE — never a hack
    around the boundary, never a native escape.
  - You are confined to a workdir that is the config layer; you cannot reach
    host source (`*.ex`) or another tenant's repo.
  - Diffable + reversible: every change is a commit; a bad one is revertible.
