#+TITLE: Extensions — Orb/WASM runtime extensions for the deploy-kit
#+DATE: 2026-06-07
#+STATUS: ASSESSMENT + PLAN (research; not yet built)

This doc assesses *runtime-level extensions authored in Elixir via Orb*
(Elixir→WebAssembly DSL), compiled to WASM and run in the runtime's existing
capability-gated component sandbox. The verdict up front, then the evidence.

* TL;DR (read this, skip the rest if pressed)
1. *The architecture is right and already exists.* An "extension" = a
   capability-gated WASM *component* on the existing =wit/engine.wit= Dock
   interface, built by =PackageManager=, instantiated by =Instance= under
   =Policy=. That substrate ships today for Rust (=cargo-component=) and JS
   (=jco=). Nothing new is needed at the sandbox layer; what's missing is the
   *authoring frontend* and a couple of *new host capabilities* (browse).
2. *Orb does NOT fit as the authoring layer today.* Orb is alpha: it emits Core
   WebAssembly 1.0 as =.wat= text (binary =.wasm= compiler still incomplete),
   and explicitly has *no component model, no WIT, no WASI*. The Dock is a
   component-model interface with WIT-typed imports. Orb cannot declare or import
   that interface. It is the wrong shape *for this surface*, right now.
3. *Recommendation:* ship the extension system on the *Rust-component +
   JS* authoring paths that already produce real WIT-typed components against
   =engine.wit=. Treat *Orb as a future Elixir frontend*, gated on its
   component-model/WIT maturity — track it, prototype against =OrbExtismPDK= when
   it lands, but do not block the extension product on it.
4. *Toolkits vs extensions:* keep both words; layer them. A *toolkit* is the
   agent-facing org/skill front-door (discovery + recipes). An *extension* is a
   sandboxed WASM *implementation*. An extension can *back* a toolkit's CLI (the
   =toolkits.ex= moduledoc already says the clean-room CLI is a WASM
   =run-command=). Don't merge the terms; one describes discovery, the other an
   artifact.
5. *"Am I reinventing containers?"* No. WASM components and OS containers solve
   different layers and you already use *both*: a Firecracker/libkrun *microVM*
   at the deployment boundary, *WASM components* for the untrusted extension code
   inside it. Capability-based, function-granular, in-process, microsecond-start,
   zero ambient syscalls — that is a strictly *tighter* model than a container
   for 3rd-party code, and the capability gate doubles as the telemetry point
   (per IDENTITY-GIT-MONOREPO.org). Complementary, not duplicative.

* What an "extension" actually is (confirming the model)
The prompt's proposed architecture is *correct as stated*. Mapped to code:

| Concern              | Existing mechanism                                    |
|----------------------+-------------------------------------------------------|
| Capability surface   | =wit/engine.wit= world =engine= (the Dock)            |
| Build untrusted src  | =PackageManager.build_dir/2= (=cargo component= / jco)|
| Sandboxed compile    | =Sandbox= (bwrap / sandbox-exec, network-denied)      |
| Capability gate      | =Policy= profiles → caps → which Dock imports exist   |
| Host-side SDK        | =Instance.Imports.for_caps/3= (one closure per cap)   |
| Run + isolate        | =Instance= (Wasmex.Components, StoreLimits, CPU cap)  |

An extension is therefore *not a new subsystem* — it is the Workbook-component
path pointed at a 3rd-party-authored component instead of a first-party one. The
only genuinely new work is (a) an authoring SDK + registration/DX, and (b)
exposing more host capabilities (browse) through the Dock.

** The host-capability SDK = the Dock imports (confirmed, with one correction)
=engine.wit= today imports =session-info=, =vfs-query=, =run-command=, plus
=llm-complete= / =net-fetch= landing with the network profile. =Instance.Imports=
binds each to a plain Elixir closure, gated by =Policy.caps/1=. *This IS the
host-capability SDK.* The "SDK" an extension author links against is exactly the
set of WIT imports their granted profile exposes.

Correction to make explicit: the WIT file is currently *narrower* than the doc
prose — it declares =session-info=, =vfs-query=, =run-command=, =run=. =llm= and
=net= are referenced in moduledocs/Policy caps but not yet in the =.wit= world.
Adding extension host-caps = the same three-line move each time:
1. Add the import to =wit/engine.wit= (typed signature).
2. Add a =Policy= cap name + put it in the profiles that grant it.
3. Add an =Instance.Imports.add/3= clause binding it to native Elixir.

For things WASM cannot do — network, TLS-fingerprinting, headless browser — the
extension must call *into the host*, never reimplement. =browse.ex= is the
worked example: a pluggable native provider (=Native= / Exa / Firecrawl, proxy
rotation) behind =fetch/crawl/search=. The extension path is: add
=browse-fetch: func(url: string) -> string= (and =browse-search=) to the Dock,
gate behind a =browse= cap, bind the closure to =Workbooks.Browse.fetch/2=. The
untrusted Orb/Rust/JS code then *calls* browse; it gets TLS impersonation and the
real browser for free and never holds a socket. This is the canonical pattern for
every "WASM can't do this" capability.

* Orb assessment (the load-bearing finding)
Sources: github.com/RoyalIcing/Orb, royalicing.com/2023/introducing-orb,
useorb.dev. State as of mid-2026:

- *Maturity:* alpha, "active development," goal is to "complete a =.wasm=
  compiler to reach beta." It currently emits *WAT text*, not binary wasm.
- *Target:* Core WebAssembly 1.0 instructions. Tiny output, zero runtime, no
  embedded Elixir at runtime (good — it is a true compile-to-wasm, not a port of
  BEAM).
- *Explicitly NOT supported:* the *component model*, *WIT* interface types, and
  *WASI* ("not stabilized yet"), no DOM.
- *Stdlib:* SilverOrb (strings/memory helpers) is WIP.
- *Extism PDK:* =OrbExtismPDK= (write Extism plugins in Elixir with Orb) is
  "coming later" — not available.

*Why this is disqualifying for the Dock, today.* The Dock is a component-model
interface; =Instance= runs components via =Wasmex.Components= with WASI-P2
linkage; capability gating works because a component that *imports* an ungranted
WIT function fails to instantiate. Orb cannot *declare WIT imports* at all, so:
- An Orb module cannot import =vfs-query= / =browse-fetch= as component-model
  functions. There is nothing for =Policy= to gate "by construction."
- =wasm-tools component new --adapt= (the bridge =PackageManager= already uses for
  Javy core modules) only attaches the *WASI preview1 adapter*; it does *not*
  synthesize custom WIT imports. So even after wrapping an Orb core module into a
  component, the host-capability SDK imports would have to be *hand-authored* in
  WAT + a hand-written WIT — defeating the "easy, familiar Elixir" goal.
- No WASI means no stdin/stdout filter path either, so Orb can't even ride the
  Javy =run-command= leaf cleanly.

*Orb's two plausible bridges, and why neither is ready:*
1. *Wait for Orb component-model + WIT support* — on the roadmap by implication
   (the =.wasm= compiler is the prerequisite) but not committed/dated. This is
   the clean path: Orb emits a real component importing =engine.wit=, drops into
   =PackageManager= unchanged. Track it; do not block on it.
2. *Extism PDK shape (=OrbExtismPDK=)* — Extism defines a *simpler host-function
   ABI* over core wasm (exactly the "call host capabilities like functions"
   ergonomics wanted here). But Extism is a *parallel sandbox runtime/ABI*, not
   the component model. Adopting it would *fork the sandbox model* — two
   capability systems, two telemetry chokepoints, two policy layers. That
   violates the "the capability gate IS the telemetry point" invariant in
   IDENTITY-GIT-MONOREPO.org. *Do not adopt Extism as a second runtime.* (If Orb
   ships an Extism PDK before a component PDK, the right move is a thin
   *host-side Extism→Dock shim* only if Elixir authoring is urgent — flagged as a
   tradeoff, not a recommendation.)

** Recommendation on the authoring layer
- *Ship now* on the languages that already produce WIT-typed components against
  =engine.wit=:
  - *Rust component* (=cargo component=, =[package.metadata.component]= →
    =PackageManager.build_dir(dir, "rust")= already routes to it). This is the
    reference authoring path — full WIT, full capability gating, today.
  - *JS* (=jco componentize= against a WIT world — =componentize_typed/3= already
    does this). Lower barrier than Rust, real components.
- *Position Orb as the future Elixir frontend.* The audience-fit argument
  ("they already know Elixir") is real and worth pursuing — but it is an
  *ergonomics upgrade on a working substrate*, not the substrate itself. Prototype
  an Orb extension the moment Orb can declare WIT imports (or via its component
  PDK). Until then, "Elixir-authored extensions" is aspirational; "Rust/JS
  capability-gated extensions" is shippable and is *the same architecture*.
- *Alternatives if a non-Rust, non-JS, low-ceremony language is wanted sooner:*
  AssemblyScript (TS-like → wasm, but same component-model gap as Orb — needs jco
  or hand WIT), or hand-written WAT (full control, no ergonomics). None beats
  "Rust component now, Orb later." Recommend not spreading thin.

* Naming + toolkit alignment
Three terms are in play: *toolkit*, *extension/plugin*, *capability*.

- *capability* — a Dock import (a host power: vfs, llm, net, browse). Gated by
  Policy. This word is settled; keep it.
- *toolkit* (=toolkits.ex=) — an *agent-facing* discovery node: a =:toolkit:=-
  tagged org headline naming a CLI + a =SKILL_DIR= of recipes the agent reads on
  demand. It is *trusted*, about *agent competence*, discovered by
  =(tags :toolkit:)=. Its moduledoc already states the clean-room CLI is a *WASM
  =run-command=*, not a native PATH binary.
- *extension* (proposed) — a *deployment-facing* sandboxed WASM *component*
  implementing =engine.wit=. *Untrusted* 3rd-party code the deployer opts into.

*Recommendation: keep both, layer them, do not unify the word.*
- They answer different questions: a toolkit answers "what can the agent do and
  how," an extension answers "what untrusted artifact runs in the sandbox."
- They *compose*: an extension is one valid *implementation* backing a toolkit's
  =CLI_BIN= (the WASM =run-command= the moduledoc already anticipates). So a
  deployer ships an *extension* (artifact) and optionally exposes it to agents via
  a *toolkit* manifest (discovery + skills). Toolkit = front-door; extension =
  what's behind the door.
- *Unify only the discovery surface.* Give extensions an =:extension:= org tag +
  manifest in the same Context-Tree shape toolkits use, so =(tags :extension:)=
  is the registry query and there is *one* discovery mechanism, not two
  subsystems. (Mirrors TOOLKIT-DISCOVERY.org: org + the kernel, no new infra.)
- *Naming call:* use *extension* as the public term (developer-facing, neutral,
  matches "extend the runtime"). Reserve *plugin* as a synonym in copy only;
  avoid "service-plugin" (collides with ServiceHost/long-lived daemons — an
  extension is request-scoped compute, not a daemon).

* The "am I reinventing containers?" answer (state this plainly to Shane)
*No — and you are already running both layers, by design.*

| Axis            | OS container (Docker/microVM)      | WASM component (the Dock)         |
|-----------------+------------------------------------+-----------------------------------|
| Granularity     | process tree                       | a function / module               |
| Isolation       | namespaces + cgroups, shared kernel| linear memory + no ambient authority|
| Authority model | *ambient* (syscalls), then dropped | *capability* (only granted imports exist)|
| Attack surface  | the whole syscall ABI              | the WIT imports you wrote — nothing else|
| Start cost      | ms→s (microVM), ms (container)     | microseconds; in-process in BEAM  |
| Telemetry point | host/agent at the OS edge          | the capability gate *is* the boundary|
| Enforcement     | configured (seccomp/AppArmor)      | *by construction* (un-imported = un-callable)|

CORRECTION (2026-06-07): the prose below says "microVM" — that is INACCURATE.
We are NOT using microVMs (no Firecracker/libkrun). The whole runtime is wrapped
in ONE portable Linux container (OCI/Docker), local now for deployment isolation
(instead of seatbelt) and the same image in cloud. Read "microVM" → "portable
Linux container" throughout this doc. The two-layer ARGUMENT still holds verbatim
(an outer OS-isolation layer + the inner WASM capability layer); only the
outer-layer technology name changes — container, not microVM.

The substrate already runs the *whole runtime inside ONE portable Linux container*
(OCI/Docker — see =PackageManager= moduledoc). That container is the *deployment*
boundary: it isolates the runtime from the host. Containers are not being
reinvented — they are the *outer* layer and stay.

WASM components are the *inner* layer for *untrusted extension code*, and there a
container would be the *wrong* tool: too coarse (process, not function), ambient
by default (you must subtract authority; WASM you must add it), heavyweight to
spin per-call, and — decisively — *the capability gate would no longer be the
telemetry/enforcement point*. The IDENTITY plan's "completeness mandate" hinges
on the component model being the chokepoint: "a component can do NOTHING except
through an interface we implement, so nothing escapes." A container breaks that
invariant — it has a kernel underneath. So the WASM-component path is not a
worse container; it is the *correct sovereignty model* for sharing untrusted code
into another deployment's sandbox: deny-by-default, function-granular,
in-process, and self-instrumenting. Containers stay where they belong (the VM
tenancy boundary); components own the untrusted-extension boundary.

*One-liner for Shane:* "Containers isolate a *process from a kernel*; the Dock
isolates a *function from everything but the capabilities you handed it*. You
need both, at different layers, and you already have both."

* Authoring SDK — what an extension author writes
The *target shape* (independent of frontend language) is one component exporting
=run= and importing the capabilities it declares:

- *Manifest* (=extension.org=, =:extension:=-tagged): name, the *capability list*
  (= the Policy profile it requires), entrypoint, version, author DID.
- *Capability imports* = the WIT imports of =engine.wit= the code calls. Declaring
  more than the granted profile allows ⇒ fails to instantiate (the gate).
- *Entrypoint:* =export run: func(input: string) -> string= (the existing world
  export). Structured I/O is JSON over that string until a richer WIT lands.

Reference (Rust, today):
#+begin_src rust
wit_bindgen::generate!({ world: "engine" });
struct Ext;
impl Guest for Ext {
    fn run(input: String) -> String {
        let page = browse_fetch("https://example.com");   // host cap
        let rows = vfs_query("select 1");                 // host cap
        serde_json::json!({ "ok": true }).to_string()
    }
}
export!(Ext);
#+end_src
The *Orb* equivalent is the goal once Orb can emit a component importing
=engine= — author an Orb module, declare the same imports, export =run=. Until
then this is Rust/JS; the SDK contract (manifest + caps + =run=) is
*language-agnostic and stable*, so the Orb frontend is a drop-in later.

* Deploy-kit DX — adding an extension at deploy time
The developer experience the prompt asks for, concretely:
1. =wb deploy= reads the workspace manifest. Extensions are declared members:
   =extensions: [./ext/brand-enrich, did:plc:…/some-shared-ext]= (local dir or
   DID-referenced, per the IDENTITY embed-vs-reference model).
2. Each extension's =extension.org= declares its required capability profile. The
   deployer *reviews and grants* — the deploy-kit surfaces "this extension
   requests: vfs, browse, llm" and the deployer approves a Policy profile. (This
   is the consent point for untrusted 3rd-party code.)
3. Build: =PackageManager= compiles each extension under =Sandbox= (network-
   denied), content-addressed. Shared/DID extensions resolve + verify (C2PA /
   author DID) before build.
4. Register: the extension's =:extension:= node joins the Context Tree;
   =(tags :extension:)= is the registry. If exposed to agents, a =:toolkit:= node
   points its =CLI_BIN= at the extension.
5. Invoke: callable as a Dock-backed component (=Instance.call/3=) and/or as a
   =run-command= leaf for agents — same as any Workbook component.

* Phased build plan
- *Phase 0 — Substrate confirmation (mostly done).* Verify the Rust-component
  authoring path end-to-end against =engine.wit=: a 3rd-party crate importing a
  gated cap fails to instantiate without it, succeeds with it. This proves the
  whole model with zero new code. (=build_dir= + =Policy= + =Instance= already
  exist.)
- *Phase 1 — Host-capability expansion.* Land =llm-complete= / =net-fetch= in the
  =.wit= (today only in prose), then add =browse-fetch= / =browse-search= imports
  → =browse= Policy cap → =Instance.Imports= closures over =Workbooks.Browse=.
  This is the "WASM can't do it, host provides it" SDK, made real.
- *Phase 2 — Extension manifest + registry + DX.* =extension.org= schema,
  =:extension:= discovery (reuse =Toolkits.discover_dir= shape), deploy-kit grant
  prompt, DID-referenced shared extensions, C2PA/author-DID verify on resolve.
  Per-extension telemetry rides the existing capability-gate chokepoint for free.
- *Phase 3 — JS authoring ergonomics.* Document/scaffold the =jco= component path
  for extension authors (lower barrier than Rust).
- *Phase 4 — Orb frontend (gated on Orb maturity).* When Orb emits a component
  importing =engine= (or ships a usable component PDK), add the Elixir authoring
  path: =PackageManager.build_dir(dir, "elixir-orb")=. Spike =OrbExtismPDK= when
  it lands *only* to evaluate, not to adopt Extism as a runtime.
- *Phase 5 — Cross-deployment sharing.* Untrusted extension shared by DID, run in
  another deployment's sandbox (the long-term vision). Rides the Composition
  rail in IDENTITY-GIT-MONOREPO.org: DID-referenced member, runtime broker edge,
  capability grant at the receiving deployment. The sandbox guarantees make this
  safe by construction.
