* What this doc is

  Two things held together: (1) the guiding principles we keep in mind while
  building the authoring service — distilled from what the broader agent
  community is converging on — and (2) the COMPOSITION SURFACES, i.e. every way
  a toolkit can be put together with workbooks, apps, APIs, and other toolkits.

  The governing stance is *non-prescriptive*. This is a map of seams, not a
  blessed workflow. The goal is that any developer can come in and build what
  they want AND THEN SOME, by composing primitives we expose — not by following
  the one path we approved. Where this doc names a "common" composition, read it
  as an example, never a requirement.

* Guiding principles (external signal → lodestars)

  The "HTML is the new Markdown" moment (Thariq Shihipar / Anthropic, Karpathy,
  Simon Willison, mid-2026) is the market independently validating the workbook
  thesis — and stalling at static single-file HTML. We hold these as design
  lodestars, not features to copy:

  1. *Human-in-the-loop is the point.* The reason rich artifacts beat flat text
     is they pull a person back into the loop with the agent. Optimize for the
     human staying engaged, not just for machine throughput.
  2. *Separate the spec from the render.* The HTML-vs-Markdown war exists because
     people conflate them. Our invariant already dissolves it: Org/OQL owns the
     compact, diffable, machine-parseable spec; WASM owns the rich rendered
     artifact. Keep that separation sacred — it answers token-cost AND
     diffability at once.
  3. *Zero-infrastructure default.* Their whole magic is "it's just a file in a
     browser." A workbook MUST stay openable as a plain HTML file; the runtime
     (toolkits, Dock, VFS) is PROGRESSIVE ENHANCEMENT, never a gate on viewing.
     Same file, opens the same way, does more when the engine is present.
  4. *Close the loop.* Their best bridge back to the agent is a manual "copy as
     prompt" button. Our differentiator: the artifact can ACT — call a toolkit,
     query the VFS, invoke an agent — through the Dock. The button runs the thing.
  5. *The host holds the credential.* Single-file HTML can't embed API keys
     safely (Simon's wall). Capability-gated Dock calls mean the artifact reaches
     an API without ever holding the secret or the socket.
  6. *Durable and distributable, not throwaway.* Their micro-apps are discarded;
     their 150 tools are one-offs with "no versioning or rollback." A toolkit is
     content-addressed, signed, version-pinned, shareable. Throwaway is allowed,
     but never forced.
  7. *Open and composable beats opinionated.* The previous six are values, not
     constraints. We expose primitives and seams; we do not prescribe how they
     combine. If a composition is physically possible on the substrate, an author
     should be able to reach it without our blessing.

* The composition surfaces (the axes an author composes along)

  A toolkit is positioned independently on each of these axes. They are
  orthogonal — pick any point on each; the substrate does not couple them.

  | Surface       | The open choice                                                        |
  |---------------+------------------------------------------------------------------------|
  | *Authoring*   | any compiler-fabric language (Rust/C/Zig/Go/JS/TS; Orb for glue)        |
  | *Shape*       | #+EXEC: command / component / kernel / task / federation               |
  | *Capability*  | any subset of Dock caps it's granted (vfs/commands/llm/browse/net/…)    |
  | *Invocation*  | agent(bash) · workbook HTML(Dock) · workflow · fabric(hot loop) · another toolkit |
  | *Packaging*   | standalone · bundled inside a workbook · published to the registry      |
  | *Distribution*| session-local → workspace(.wbundle) → registry → desktop/server tiers    |
  | *Trust*       | first-party · third-party(granted) · signed(did:key)                    |

  No axis forces another. A Zig =kernel= can be agent-invoked; a JS =command= can
  ride a fabric loop; a third-party =component= can be bundled in a workbook or
  pulled from the registry. Cover-your-bases = every cell is reachable.

* Toolkit × Workbook — the relationships (the "can I…?" answers)

** A toolkit INSIDE a workbook (the workbook as carrier)
   A workbook's bundle (=.wbundle=: HTML + SQLite VFS + manifest) can carry
   toolkits — source (=.org=) plus their compiled =.wasm= (library.ex packs a
   workspace → one parent workbook, source inputs + build outputs). So a workbook
   is *self-contained*: open it, its toolkits travel with it. No external fetch
   required to run what it ships.

** A toolkit USED BY a workbook's HTML (the closed loop)
   The workbook's HTML calls a toolkit through the Dock (=run-command= for a
   =command=; a typed call for a =component=). This is principle #4 made real:
   the HTML front-end isn't a static picture, it drives sandboxed compute behind
   it. A "copy as JSON" button becomes a toolkit invocation. Human-facing HTML,
   WASM compute behind, VFS state beneath — one artifact.

** A toolkit ACROSS workbooks (sharing)
   Two routes, author's choice:
   - *Embed* — bundle the toolkit into each workbook that needs it (portable,
     offline, no resolution).
   - *Reference* — publish once to the registry (content-addressed + Ed25519
     signed), install by sha pin into many workbooks; or reference by did:key for
     a shared/3rd-party toolkit. (Registry = wb-rhs.7.)
   The same toolkit artifact works either way; embed vs reference is a
   distribution decision, not a different build.

** A toolkit connecting to an API (through the runtime)
   Yes — via the Dock's =browse=/=net= capability (Route B): the toolkit calls
   =browse-fetch=/=net-fetch=; the HOST performs the egress with the full browser
   stack and the credentials; the toolkit never holds a socket or a key. Gated by
   Policy, so a toolkit only reaches the network if its profile grants it. For a
   SaaS API specifically, the =federation= shape adds an OQL data-source + sync
   daemon (host-side, supervised) so the workbook can =SELECT … FROM linear-issue=
   without the agent touching the API.

** A toolkit in an app (desktop / server)
   The desktop app is workbook-native: it embeds the OQL kernel (=oql.wasm=,
   wasmtime) and runs toolkits LOCALLY, no server. So a toolkit in a workbook in
   the app runs on the user's machine. The runtime server tier can run the same
   toolkit for agent/sync workloads. Same artifact, two host tiers — the toolkit
   doesn't know or care which.

** A toolkit composing OTHER toolkits
   The =commands= cap lets a toolkit invoke another by name (=run-command= is
   itself a Dock import a toolkit can hold). Workflows orchestrate deterministic
   chains; agents drive nondeterministic ones; a fabric loops a kernel over many
   inputs. Composition is recursive and multi-paradigm by construction.

* The non-opinionated stance (the caveat, stated plainly)

  We ship PRIMITIVES and SEAMS, not policy:
  - primitives: the EXEC shapes, the Dock caps, the compiler-fabric languages,
    the VFS, content-addressing, the registry.
  - seams: the manifest (#+EXEC/#+CAPS/#+TRUST), the Dock SDK, run-command,
    the bundle format.

  What we deliberately DO NOT do:
  - No single blessed pipeline. There is no "the way" to build a toolkit; there
    are surfaces, freely combined.
  - No capability we force. Deny-by-default; an author requests only what they
    need; the deployer grants. We never widen a toolkit's reach for it.
  - No lock to one consumer. A toolkit is not "an agent thing" or "a workbook
    thing" — it serves agent, HTML, workflow, fabric, and other toolkits equally.
  - No mandated distribution tier. Session-local throwaway is as first-class as a
    signed registry release.

  The test for any new feature: does it ADD a reachable composition, or does it
  REMOVE one by making a choice on the author's behalf? Prefer the former; treat
  the latter as a smell.

* A few worked compositions (examples, not templates)

  - *Living design system* — a workbook whose HTML renders a design system from
    an org spec, with a bundled =command= toolkit that exports tokens as JSON on
    click. (The brand-book, already shipping.)
  - *Self-contained data tool* — a workbook carrying a Rust =command= that
    transforms data in the VFS; opens offline in the desktop app; no network.
  - *API-backed report* — a workbook whose HTML calls a =browse=-capped toolkit
    to pull a live source through the host, renders it, caches to VFS.
  - *Shared kernel* — a ProRes-decode =kernel= published to the registry,
    installed by sha into many video workbooks, looped by the fabric per frame.
  - *Agent that extends itself* — an agent (loaded :agent: node) that authors a
    new =command= toolkit mid-session for a gap it hit, registers it, uses it
    (wb-rhs.4) — all inside its own container.

  None of these is "the" pattern. They are five points in a space the author is
  free to move through arbitrarily.
