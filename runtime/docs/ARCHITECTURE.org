#+TITLE: Clean-room Architecture — the onion, and where everything lives
#+DATE: 2026-06-06

This is the layering contract. It answers: what is *core* vs *extension*, where
WASM components live, what Org owns vs what WASM owns, how BYOD storage plugs in,
and when core is "done" so we stop editing it and start building *on* it. The
rule the whole doc serves: *DRY by layer* — an outer layer never reaches into an
inner one's internals, and never reimplements what an inner layer already gives.

* The onion (inner → outer; each layer depends only inward)

** L0 — Core runtime (this worktree, ~2.4k LOC). The substrate. Frozen-ish.
   The BEAM host + the OQL kernel. Owns exactly the things every Workbook needs
   regardless of what it does:
   - =kernel/= — the OQL Component (=workbooks:oql=): parse · tangle · validate ·
     upgrade · render. The Org engine.
   - =host/instance.ex= + =host/instance/= — an Instance: one Wasmtime Component,
     memory-capped, calling a typed Dock; supervised per tenant.
   - =host/vfs.ex= — the Instance's SQLite state.
   - =host/package_manager.ex= — tangle a Workbook → build its components.
   - =host/lifecycle.ex= — created→active→frozen→…; freeze/resume = the SQLite file.
   - =host/auth.ex= + =host/web.ex= + =host/socket.ex= — the HTTP/WS surface.
   Core is small on purpose. It defines *behaviours and contracts*; it does not
   ship integrations. When core is done (see §"Done"), it stops changing.

** L1 — Contracts (WIT worlds + the Org grammar). The seams.
   The typed boundaries outer layers build against, so they never touch L0 code:
   - =wit/oql.wit= (=workbooks:oql=) — the kernel's exports.
   - =wit/engine.wit= (=workbooks:engine=) — the Dock a Workbook component runs
     against: =session-info=, =vfs-query=, (+ =llm-complete=/=net-fetch= as caps
     grow), and the Workbook entrypoint =run=.
   - The Org-babel grammar — =:component:= / =:workflow:= tags, header args
     (=:deps :uses :in :out :persist :dir=). This is the *manifest surface*.
   A new capability = a new WIT import + a host closure that provides it, gated by
   Policy. You extend the world; you don't fork the Instance.

** L2 — Backends / Capabilities (MODULES). Swapped at deploy, never edited into core.
   Implementations of an L0 behaviour, chosen per deploy cell:
   - *BYOD storage* — a =Backend= behaviour with impls =Backend.SQLite= (local/dev),
     =Backend.Postgres= (cloud cell), =Backend.Workbook= (an .html as a queryable
     peer). Same shape as GitWork, same shape as the old Vmm.Backend. See the
     mainline =BYOD-PLAN.org=; the clean-room mirrors that behaviour, not its bulk.
   - *Storage volumes* — where the SQLite/Postgres bytes actually live: a Fly
     volume (local file), or S3/R2 via *Litestream* WAL replication (continuous
     ship + restore). The Instance always talks SQLite; Litestream makes it
     durable off-box. Postgres is the indexed/shared path (tenant-wide search,
     presence, analytics) — org files stay the source of truth; the DB is derived.
   - *CPU cap* — the epoch-interruption backend (pending a Wasmex change; memory
     cap is live today).
   A Backend is a MODULE: it implements a core behaviour and is selected at deploy
   time. It is not a plugin (not discovered at runtime) and not core (not edited in).

** L3 — Components (the WASM guests). Agents, tools, Workbooks. The payload.
   These are what *runs inside* Instances. Authored as Org + source blocks in the
   *user's monorepo* (never in this repo), compiled to Components, content-addressed.
   - A *tool* = a small component over WASI stdio (Javy/QuickJS). Piped in a DAG.
   - A *Workbook* = a component targeting =workbooks:engine= — its =run= is the
     entrypoint; it calls the Dock for state/llm/net.
   - An *agent* = a Workbook whose =run= is a message loop. Agents are NOT a special
     core concept — they are L3 components with a particular shape. "Where do agents
     live?" → here, as components, in the user's packages — not in L0.
   This is the answer to "what's written in our WASM language": the *behaviour* of
   guests. Core never hard-codes an agent; it runs whatever component docks in.

** L4 — Plugins (OQL plugins / toolkits). Integrations. Discovered, not compiled in.
   SaaS adapters (Notion, GitHub, Stripe, Linear), web search, etc. These are *OQL
   plugins* (mainline =PLUGINS-PLAN.org=) + =:toolkit:=-tagged CLIs discovered in the
   Context Tree — read/written by agents at runtime. A plugin never links into core
   and never ships in the engine binary; it is resolved when an agent needs it.
   "If I want to build more off this system without touching core" → L4 (a plugin/
   toolkit) if it's an integration, or L3 (a component) if it's a behaviour.

** Deploy-kit — the cells that wire L2+L3 into a shippable.
   =desktop= / =cloud= / =burst= cells pick the L2 backends (SQLite vs Postgres,
   Fly volume vs R2) and bundle the L0 engine + L3 components. The recipe lives in
   deploy-kit, not in core.

* Org owns vs WASM owns (the source-of-truth split)
  - *Org owns the spec*: which components exist, their deps/edges/schedule/
    lifecycle/capabilities — the manifest + orchestration. Human/agent-authored.
    Version-controlled. The single source of truth.
  - *WASM owns the artifact*: the compiled behaviour of each source block.
    *Derived* from Org, content-addressed, ephemeral, rebuildable. Never edited by
    hand, never the source of truth.
  If they disagree, Org wins and WASM is rebuilt. This is why the runtime can be
  tiny: it carries no behaviour of its own beyond the kernel — behaviour is L3,
  authored as Org, compiled on demand.

* Plugins vs Modules vs Features — the vocabulary, settled
  - *Module* = an implementation of a core behaviour (a Backend, a CPU-cap backend,
    a GitWork backend). Lives beside core, selected at deploy. Compile-time.
  - *Plugin* = an integration (OQL plugin / toolkit). Discovered at runtime, never
    linked into core. Run-time.
  - *Component* = a WASM guest (tool / Workbook / agent). Authored in Org, run in an
    Instance. The unit of user-built behaviour.
  - *"Feature folder"* has no L0 meaning here. Its equivalent is *a component package
    in the user's monorepo* (a behaviour) or *a deploy-kit recipe* (a wiring). If you
    reach for a feature folder inside core, it belongs in L3 or deploy-kit instead.

* Command vs Toolkit vs Workflow — related, but distinct; do not conflate
  The "tool registry" name caused a conflation once, so these are pinned here.
  They are *nested*, not opposed: a Toolkit wraps a CLI; that CLI becomes
  Commands; Workflows orchestrate components that run Commands. (There is no
  separate "board" — a workflow IS the orchestration unit; see below.)
  - *Command* (L0/L1, =CommandRegistry= + the =run-command= Dock import, wb-11ck.21)
    — a CLI *converted to a runnable WASM binary*, invoked by name over
    stdin/stdout in a bash-type environment (the in-WASM shell, wb-11ck.20). The
    executable leaf. jq, ripgrep, and any toolkit's CLI live here. *Built.* A
    command may be pure-compute, or need a capability (=net-fetch= + the secret
    model) — that's a property of the command, not a different layer.
  - *Toolkit* (L4, wb-11ck.46) — *our version of Claude Code skills*. The GOAL
    (the thing to recreate canonically, not file-for-file): the agent's
    *extensibility surface* — a discoverable wrapper that makes an agent competent
    with a CLI/integration it has never seen, by shipping progressive-disclosure
    *skill recipes* alongside the thing they drive, discovered via org tags and
    read on demand. Any developer teaches the agent a new capability by dropping a
    toolkit; core is untouched. Prior art to lean on (the concept, not a verbatim
    port): =toolkits/AUTHORING.org=, =runtime/docs/TOOLKITS-PLAN.org=,
    =TOOLKIT-DISCOVERY.org= — there a toolkit is a dir of =manifest.org= +
    =skills/*.org= wrapping a CLI, discovered by the OQL query =(tags :toolkit:)=
    against an =:agent:= node's =:TOOLKITS:= list. *Clean-room fit:* the wrapped
    CLI becomes a WASM *command* (=run-command=) and discovery rides the kernel's
    tag extraction — but match the *goal*, don't overbuild. *Mostly unbuilt here.*
    bash/the Dock stays the agent's one tool; a toolkit is a discovered org+CLI
    surface, never a new core entry.
  - *Workflow* (above L1, wb-11ck.47) — *orchestration*. There is no separate
    "board" abstraction: a native Org =:workflow:= IS the DAG. Its =:component:=
    children are the *tasks*, =:out=→=:in= header args are the edges, nested
    =:workflow:= headings are sub-workflows. Workflows and tasks make up the DAG.
    =Workbooks.Workflow.run= executes it recursively (topological, piping along
    edges) → a run record + schedule. The tasks run *commands* (a toolkit's CLI)
    via the shell. *Built.*
  Rule of thumb: a CLI made runnable → command; a skill-doc + its CLI → toolkit;
  a DAG of tasks → workflow. Secrets/network is an orthogonal *capability*
  (=docs/SECRETS.org=) some commands need, not a layer of its own.

* When is core "done"? (the line after which we build *on*, not *in*)
  Core is done when an Instance can, for any docked component:
  1. *run* it (Component Model)              — DONE
  2. give it a typed *Dock* (state/llm/net/session) — session+vfs DONE; llm/net next
  3. *isolate* it (memory + CPU)             — memory DONE; CPU = L2 epoch backend
  4. *persist* it (freeze/resume)            — VFS DONE; linear-memory snapshot = TODO
  5. *build* it (tangle → component)         — tool path DONE; engine-component spine next
  6. *serve* it (web/ws)                     — DONE
  7. *authenticate* it (Guardian/JWKS)       — local DONE; JWKS prod next
  8. *version* it (git/Radicle)              — DONE
  9. *store* it (BYOD backend behaviour)     — SQLite DONE; Backend behaviour + Postgres next
  When 1–9 are green, L0 is frozen. Everything after is L2 (backends), L3
  (agents/tools/Workbooks), L4 (integrations), deploy-kit (cells) — none of which
  edits L0. That is the whole point: lock the substrate, grow the onion outward.

* Feature parity with the previous branch — the target
  Not bug-for-bug parity. *Comparable capability*: run agent systems (L3 components
  with the engine Dock), a real filesystem (VFS + named volumes + BYOD), and the
  same deploy story (cells), at ~1/16th the LOC. The previous branch's 39k lines
  become: ~2.4k core + thin L2 modules + L3 authored-not-coded + L4 discovered.
