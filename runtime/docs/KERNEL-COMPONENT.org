#+TITLE: Kernel as Component — and the WASM-3.0 assessment behind it
#+DATE: 2026-06-06

* What changed
The OQL kernel (=kernel/=, built to =build/oql.wasm=) was the one piece that
opted out of the Component Model it *imposes* on user code. User JS components
go through jco/componentize-js into typed WIT components; the kernel was a raw
core module behind a hand-rolled C-ABI (=oql_alloc=/=oql_dealloc= + a packed-u64
=(ptr<<32)|len= return the host unpacked by hand).

Now the kernel is a WIT-typed Component (the =workbooks:oql= world,
=kernel/wit/world.wit=): every export is =string -> string=, built with
=cargo component build=, loaded via =Wasmex.Components=. One ABI for the whole
system.

** Deleted
- Kernel: the entire memory boundary (=oql_alloc=, =oql_dealloc=, =read_str=,
  =write_str=, the packed-u64 math) and the duplicated =#[no_mangle]= export
  bodies. lib.rs 563 -> 517 LOC despite gaining the =impl Guest= boilerplate.
- Host (=host/oql.ex=): =run/3='s alloc -> write -> call -> unpack -> dealloc
  dance, the manual =Wasmex.Memory= read/write, the 32-bit ptr assumption.

** Build
=cargo build --target wasm32-wasip1= -> =cargo component build --release=.
=src/bindings.rs= is wit-bindgen output (gitignored, regenerated each build).
The component carries unused WASI 0.2 imports (Rust std's panic/stderr); =Wasmex
.Components= satisfies them with a default context, so the host passes no WASI.
Verified: all kernel demos (parse/tangle/validate/upgrade/render) return
identical results through the typed path.

* The WASM-3.0 / ecosystem assessment (the "why only this")
Wasmex 0.14 wraps Wasmtime 39 and ships =Wasmex.Components=, so the runtime was
already new enough; the gap was our build chain, not the host.

** Act now (done)
Kernel-as-Component (above). Not a 3.0 feature — just the Component Model
finally being stable enough (jco 1.0, cargo-component) that the kernel should
stop being the exception.

** Watch — aligned, premature
- *WASI 0.3 =stream<T>= / =future<T>= for the workflow DAG.* The single most
  aligned future feature. DAG edges (=:out= -> =:in=) flow today as stdin/stdout
  byte pipes (COMPOSE-NOTES.org); 0.3 async streams are exactly that as a typed
  native primitive. Wasmtime 39 supports the preview; gap is Wasmex surfacing
  stream/future + Javy/jco emitting 0.3. Kernel-as-Component is the on-ramp.
- *Bump user components preview1 -> WASI 0.2 proper* (drop the preview1 adapter
  shim). Low urgency.
- *Spin/Fermyon (Akamai) as an edge deploy target* — possible =wb deploy
  --edge=; framework lock-in, so not now.

** No — and why
- *Memory64*: actively wrong. Our component ABI is typed now, but Org files are
  KB-MB; 4GB is absurd headroom and 64-bit bounds checks cost perf. No benefit.
- *Multiple memories*: single-tenant, single-memory kernel. No use.
- *WasmGC*: only matters for Java/Kotlin/Dart *guests*, which we don't accept;
  GC-across-component-boundary is immature anyway.
- *Exception handling / relaxed SIMD / typed-refs / WAT annotations*:
  guest-toolchain internals; Wasmtime traps our =panic=abort= kernel cleanly.
- *JS string builtins*: a browser (V8/JSC) feature; we render server-side.
- *Alt runtimes (Wazero/Chicory/WasmEdge/Spin-runtime)*: wrong host language —
  we're BEAM + Wasmtime via the one allowed NIF.
- *Extism*: a second wasm ABI/runtime; conflicts with "one NIF (Wasmex)".
- *Orb*: writes wasm in Elixir; we'd lose orgize.
- *wasi-nn / Edge.js / wasmCloud*: out of scope — no in-sandbox ML (LLM is HTTP
  egress), no whole-Node guests, no distributed-actor platform.

** Security note (no work item)
WALMA/memory-tagging research targets *intra-module* memory safety — only bites
C/C++ guests, which we don't accept. The boundary we defend (host-from-guest:
fuel + StoreLimits + no ambient WASI caps) is already covered.
