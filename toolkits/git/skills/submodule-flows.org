#+TITLE: git — submodule flows (init / update / bump / remove)
#+TOOLKIT: git
#+SKILL: submodule-flows
#+VERSION: 0.1.0
#+DESCRIPTION: Use when a repo contains git submodules and you need to clone it correctly, update a submodule pointer, add a new one, or remove one. Submodules have unusual lifecycle commands; this is the cheat sheet.
#+TAGS: vcs submodule subtree dependencies
#+STATUS: stable

* When to use this
  :PROPERTIES:
  :NETWORK: yes
  :DESTRUCTIVE: maybe
  :END:

  Working in a repo with =.gitmodules= (or about to add a
  submodule). The flow is unusual enough that even experienced
  users reach for docs every time.

  If your repo uses =git subtree= instead, that's a different
  tool — submodules track external SHAs; subtrees merge external
  history into your repo's history.

* Clone a repo that has submodules

  #+CAPTION: confirm submodules exist
  #+begin_src bash :role pre
  test -f .gitmodules || { echo "no .gitmodules — repo has no submodules"; exit 1; }
  cat .gitmodules
  #+end_src

  #+CAPTION: the one-shot incantation
  #+begin_src bash
  git clone --recurse-submodules <url>
  #+end_src

  #+CAPTION: if you already cloned without --recurse
  #+begin_src bash
  git submodule update --init --recursive
  #+end_src

* Update a submodule to a newer upstream commit

  #+CAPTION: pull the latest from the submodule's tracked branch
  #+begin_src bash
  git submodule update --remote --merge -- path/to/submodule
  # then commit the bump in the OUTER repo so the SHA-pointer moves
  git add path/to/submodule
  git commit -m "bump submodule: <reason>"
  #+end_src

  Without =--remote=, =git submodule update= just resets the
  submodule to the SHA your outer repo already points at —
  which is the right call after pulling someone else's commit
  that bumped the pointer.

* Add a new submodule

  #+CAPTION: register + clone the submodule in one step
  #+begin_src bash
  git submodule add https://github.com/owner/repo.git path/to/new-sub
  git commit -m "add submodule: <name>"
  # creates .gitmodules entry + checks out the submodule + commits
  #+end_src

* Remove a submodule (the painful flow)

  Removing requires touching 3 places: =.gitmodules=,
  =.git/config=, and the working tree.

  #+CAPTION: 1. de-init the submodule (clears .git/config entry)
  #+begin_src bash
  git submodule deinit -f path/to/sub
  #+end_src

  #+CAPTION: 2. remove from index (clears .gitmodules entry)
  #+begin_src bash
  git rm -f path/to/sub
  #+end_src

  #+CAPTION: 3. clean up .git/modules cache (else re-add fails)
  #+begin_src bash
  rm -rf .git/modules/path/to/sub
  #+end_src

  #+CAPTION: 4. commit
  #+begin_src bash
  git commit -m "remove submodule: <name>"
  #+end_src

* Working with submodules inside worktrees

  Each worktree needs its own submodule init. After =git
  worktree add ...= you typically need:

  #+begin_src bash
  cd ../new-worktree
  git submodule update --init --recursive
  #+end_src

  See [[file:worktree-management.org][worktree-management]] for the worktree side.

* Common pitfalls

  1. *Forgot =--recurse-submodules= on clone.* Repo looks
     broken (missing files in submodule paths). Fix: =git
     submodule update --init --recursive=.

  2. *Bumped submodule but forgot to commit the bump.* The
     submodule directory shows "new commits" in =git status=
     but you never =git add= the path. Pull in your team sees
     the OLD SHA. Fix: =git add <path> && git commit=.

  3. *Re-adding a submodule that wasn't fully removed.* If
     step 3 (=rm -rf .git/modules/<path>=) was skipped, git
     complains "already exists in the index". Run step 3 then
     retry add.

  4. *Detached HEAD inside submodule.* Default state. Don't
     panic — submodule checkouts are SHA-pinned, not branch-
     tracking. If you want to ITERATE on the submodule, =cd
     <sub> && git checkout main= (or whatever), then bump.

  5. *Modified submodule contents not staged.* Changes inside
     a submodule's working tree don't get added by =git add
     .= in the outer repo. =cd= into the submodule + commit
     there, push, then update the pointer in the outer repo.

* Verification checklist

  - [ ] =git status= clean after the operation
  - [ ] =.gitmodules= reflects intent (paths + URLs match what you wanted)
  - [ ] Submodule dirs are populated (=ls path/to/sub/ should not be empty=)
  - [ ] If updated: outer repo committed the new SHA pointer
