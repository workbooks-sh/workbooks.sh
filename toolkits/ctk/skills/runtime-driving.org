* When to use this
  :PROPERTIES:
  :NETWORK:     no
  :DESTRUCTIVE: no
  :COST:        free
  :END:

  Use when something OTHER than a human's mouse needs to operate a CTK story —
  the runtime loading the toolkit, or an agent proposing control values for a
  human to approve. CTK is the *bench*; this is how the loop reaches into it.

  NOT for authoring a story (see [[file:authoring-a-story.org][authoring-a-story]]) or first-contact
  ([[file:overview.org][overview]]).

* The mental model — one drivable surface, two transports

  Every CTK shell exposes the same surface; a driver reads the spec, sets
  controls, and snapshots state. There is no separate "automation API" — the
  controls a human moves and the ones a driver sets are the *same* props.

  Two transports onto that surface:

  1. *In-page* — =window.CTK= (same realm: an agent in devtools, an injected
     script, or the host page).
  2. *Cross-frame* — =postMessage= (the runtime serves the shell in an iframe /
     webview and drives it from outside its realm).

* The surface — =window.CTK=

  | Call                  | Returns / effect                                        |
  |-----------------------+---------------------------------------------------------|
  | =CTK.stories=         | the story ids the shell knows                           |
  | =CTK.current=         | the loaded story id                                     |
  | =CTK.load(id)=        | switch story (re-parses spec, re-imports source)        |
  | =CTK.spec()=          | the raw Org control-spec text of the current story      |
  | =CTK.controls()=      | shared (prop) control defs: =[{prop,type,default,...}]=  |
  | =CTK.states()=        | =[{state, overrides, controls}]= — states + per-state controls |
  | =CTK.props()=         | the live SHARED prop values                             |
  | =CTK.stateProps(name)=| the live per-state control values for one state         |
  | =CTK.get(prop)=       | one shared prop value                                   |
  | =CTK.set(prop, v)=    | set a shared prop — re-renders all states + reflects in panel |
  | =CTK.setStateProp(name, prop, v)= | set one state's per-state control               |
  | =CTK.snapshot()=      | ={ story, props, states }= — props + each state's effective props |

  =set= coerces by the control's declared type (range→number, toggle→bool), so a
  driver can pass strings safely.

* The postMessage protocol (cross-frame)

  The host posts =message= events with =ctk: true=:

  #+begin_src js
  // host → shell
  frame.contentWindow.postMessage({ ctk: true, action: "load", story: "button" }, "*");
  frame.contentWindow.postMessage({ ctk: true, action: "set", prop: "variant", value: "danger" }, "*");
  frame.contentWindow.postMessage({ ctk: true, action: "snapshot" }, "*");
  // shell → host (reply to snapshot)
  // { ctk: true, reply: "snapshot", data: { story, props } }
  #+end_src

* The human-in-the-loop loop (what the runtime does)

  1. *Serve* the toolkit shell (render EXEC) — e.g. the runtime serves
     =ctk.html= + =stories/= and opens it in a webview/iframe.
  2. *Read* the spec: =CTK.spec()= / =CTK.controls()= → the agent learns the
     knobs without guessing.
  3. *Propose*: the agent =set=s control values (a candidate it built).
  4. *Observe*: a human sees the rendered stage; =CTK.snapshot()= captures the
     exact state for the record / for the agent's next step.
  5. *Approve / iterate*: the human tweaks (same controls), the agent reads the
     new snapshot, continues. That handoff IS the human-in-the-loop step.

* Common pitfalls

  1. *Driving before load* — =CTK.set= before the first story resolves no-ops.
     Wait for =CTK.current= to be set (the shell loads story[0] on boot).
  2. *Cross-origin frame* — reading =frame.contentWindow.CTK= across origins
     throws; use =postMessage= when the shell is served from another origin.
  3. *Assuming a prop exists* — =set= on an unknown prop just stores a dead
     value the component ignores. Read =CTK.controls()= first.
  4. *Treating snapshot as the artifact* — the snapshot records control state,
     not the component source; the source is the story's =:tangle= block.

* Verification checklist

  - [ ] Serve the dir (=python3 -m http.server 5180=) and open =ctk.html=.
  - [ ] In devtools: =CTK.controls()= lists the story's props.
  - [ ] =CTK.set("size", 100)= moves the slider AND re-renders.
  - [ ] =CTK.snapshot()= returns the current ={story, props}=.
  - [ ] From a parent frame, a =postMessage= =set= changes the stage.

* Status / what's next

  The drivable surface (=window.CTK= + postMessage) ships in the shell today.
  The remaining integration is runtime-side: a route that SERVES the toolkit and
  a host that drives it over postMessage, plus persisting approved snapshots.
  Tracked under the platform/render-toolkit work; mark this skill =stable= once
  a runtime round-trip is verified.
