# open-avatars — packs

# When to use this

Read this when your task is to *understand the pack format* or to *add a new
avatar pack* (a new style — the toolkit is built to carry many). The toolkit is
*type-dispatched*: a pack declares a `type` and the single `avatar()` routes to
the right renderer. Pick the type that fits your art before you start.

# The three pack types (and what `avatar()` does with each)

A pack's `pack.json` declares `"type"`. `avatar(pack, seed, opts)` dispatches on it:

| `type`        | The art is…                                     | `avatar()` returns           | Sub-kind         |
|---------------|-------------------------------------------------|------------------------------|------------------|
| `assembled`   | atoms composed by category + offsets            | one composed `<svg>`         | —                |
| `gallery`     | a list of WHOLE, finished avatars               | one picked avatar            | `svg` / `raster` |
| `procedural`  | a pure `generate(seed,opts)→svg` the pack ships | whatever `generate()` returns | —              |

Determinism is identical across all three: selection is *FNV-1a over a SORTED id
list* (gallery) or over a sorted category-name list (assembled); procedural packs
own their algorithm but must be pure (same seed → same string, forever).

Back-compat: a bundle with no `type` but a `categories` map is treated as
`assembled`, so the original open-peeps bundle works untouched.

# type: assembled — compose atoms (the open-peeps path)

# Anatomy of an assembled pack

```
packs/<name>/
  atoms/
    body/         *.svg   one atom per option
    head/         *.svg
    face/         *.svg
    facial-hair/  *.svg   includes "None.svg" (the empty option)
    accessories/  *.svg   includes "None.svg"
  reference/      one or more official compositions (the calibration witness)
  pack.json       hand-written calibration (canvas, offsets, z-order, crops)
  pack.bundle.json  GENERATED by scripts/bundle-pack.mjs — atoms + pack.json
```

The renderer only ever reads `pack.bundle.json`. `pack.json` is the human input;
the bundler merges it with the stripped atoms.

# The `pack.json` format

```json
{
  "name": "open-peeps",
  "canvas": [1136, 1533],
  "categories": {
    "body":        { "dir": "atoms/body",        "viewBox": [818, 733], "offset": [147, 639], "z": 0, "optional": false },
    "head":        { "dir": "atoms/head",        "viewBox": [473, 567], "offset": [372, 180], "z": 1, "optional": false },
    "face":        { "dir": "atoms/face",        "viewBox": [289, 293], "offset": [531, 366], "z": 2, "optional": false },
    "facial-hair": { "dir": "atoms/facial-hair", "viewBox": [280, 230], "offset": [495, 518], "z": 3, "optional": true  },
    "accessories": { "dir": "atoms/accessories", "viewBox": [392, 138], "offset": [419, 421], "z": 4, "optional": true  }
  },
  "crops": {
    "circle": { "cx": 605, "cy": 470, "r": 355 },
    "bust":   { "viewBox": [0, 110, 1136, 900] },
    "full":   { "viewBox": [0, 0, 1136, 1533] }
  }
}
```

- `canvas` — `[w, h]` of the master composition (the reference's viewBox).
- `categories.<cat>`
  - `dir` — where the atoms live, relative to the pack dir.
  - `viewBox` — `[w, h]` shared by *every* atom in that category. (This is the
    key invariant: a category exports all atoms on one common viewBox, so a
    *single* offset aligns every atom in it. Verify by reading one atom per
    category.)
  - `offset` — `[x, y]` translate of this category's group within the canvas.
    Lifted verbatim from the reference composition's group transforms.
  - `z` — paint order, back→front. Lower draws first.
  - `optional` — `true` if a "None" atom is a valid pick (the empty option).
- `crops`
  - `circle` — `cx, cy, r` of the avatar disc. Frame the head+face: derive from
    the head `offset` + `viewBox` (head center ≈ `offset + viewBox/2`), nudge `cy`
    down toward the face and pick `r` to enclose the head with a little margin.
    The renderer turns this into a square `viewBox` + a `clipPath` circle.
  - `bust` / `full` — explicit `[x, y, w, h]` viewBoxes into the canvas.

# The bundler — `scripts/bundle-pack.mjs`

```bash
node scripts/bundle-pack.mjs <name>      # default: open-peeps
```

For each atom it strips the Sketch export down to the inner drawable: it drops
the `<?xml>` prolog, the `<!--Generator-->` comment, `<title>`/`<desc>`, and the
root `<svg>` wrapper, keeping the inner `<g>…</g>`. An atom whose group is empty
(the `None` option → `<g …></g>`) normalizes to ="", so it is a true empty
pick — the renderer emits *nothing* for it (no hollow group). The output is
`pack.bundle.json` ` `{ ...pack.json, atoms: { <cat>: { <name>: <inner> } } }=.

# HOW TO ADD AN ASSEMBLED PACK

1. *Drop atoms.* Create `packs/<name>/atoms/<cat>/*.svg`. Keep the categories
   you want (`body/ head/ face/`… or your own taxonomy — the renderer is generic
   over category names; only the calibration is pack-specific). Ensure every
   atom in a category shares one viewBox (export them that way).

2. *Get a reference composition.* Drop the style's official assembled figure in
   `packs/<name>/reference/`. This is your ground truth for offsets *and*
   z-order — you read the per-category `translate(x, y)` straight off its group
   transforms, and you confirm the paint order by eye.

3. *Write `pack.json`.* Fill `canvas` (the reference viewBox), and for each
   category its `dir`, shared `viewBox`, `offset` (from the reference's group
   transform), `z` (paint order), and `optional`. Compute the `circle` crop from
   the head. Set `bust`/`full` viewBoxes.

4. *Bundle.* `node scripts/bundle-pack.mjs <name>`.

5. *Verify alignment.* Render a few seeds at `full` crop and rasterize
   (`rsvg-convert avatar.svg -o avatar.png`) or open them in a browser; compare
   to the reference. Faces must sit ON heads, accessories on the eyes, etc. If a
   category drifts, the fix is its `offset` in `pack.json` — re-bundle, re-check.
   Add the pack's seeds to a specimen section if you want it in the proof page.

# Done-when (assembled)

`pack.bundle.json` exists, a handful of seeds render with every category aligned
to the reference, and "None" picks render cleanly (no broken group). The
renderer was *not* touched — all pack knowledge lives in `pack.json`.

# HOW TO ADD A GALLERY PACK (whole, finished avatars)

A gallery pack picks ONE complete avatar by seed. Two kinds:

## kind: svg — whole inline SVG figures (e.g. transhumans)

1. *Drop figures.* `packs/<name>/figures/*.svg` — one finished character per
   file. They keep their *native art and color* (gallery packs are not
   monochrome-by-law; that rule is only for assembled atom packs).
2. *Write `pack.json`.*
```json
   { "name": "<name>", "type": "gallery", "kind": "svg",
     "license": "…", "credit": "…", "dir": "figures",
     "viewBox": [1080, 1080] }
```
   `viewBox` is the figures' shared `[w,h]`. If a figure exports at a different
   ratio the renderer centers it in a square `max(w,h)` viewBox — read one file's
   `viewBox` to set this.
3. *Bundle.* `node scripts/bundle-pack.mjs <name>` → `pack.bundle.json` =
   `{ ...pack.json, items: { "<id>": "<inner svg>" } }` (id = the filename).
4. *Verify.* `avatar(bundle, seed)` returns the chosen figure framed to a square;
   `pick(bundle, seed)` returns the chosen id (FNV over the sorted id list).

## kind: raster — a big set of bitmaps you DON'T inline (e.g. pixabots)

For thousands of raster avatars, inlining is absurd (13 MB+). Instead the bundle
records only the *id list* + a *path template*; `avatar()` returns an `<img>`.

1. *Stage rasters.* `packs/<name>/<dir>/<id>.<ext>` (e.g. `webp/<id>.webp`) plus a
   `manifest.json` with an `"ids"` array (or let the bundler list the dir).
2. *Write `pack.json`.*
```json
   { "name": "<name>", "type": "gallery", "kind": "raster",
     "license": "…", "credit": "…",
     "path": "<id>.webp", "base": "webp/", "idsFile": "<name>.ids.json" }
```
   - `path` — template; `<id>` is substituted with the chosen id.
   - `base` — default prefix for the `src` (a consumer overrides with `opts.base`
     to point at wherever THEY host the bitmaps).
3. *Bundle.* `node scripts/bundle-pack.mjs <name>` emits the *tiny* `<name>.ids.json`
   (`{ ...pack.json, ids: [...] }`) — the rasters are NOT inlined.
4. *Use.* `avatar(idsBundle, seed, { base: "https://cdn…/" })` →
   `<img src`"https://cdn…/<id>.webp" …>`. Default base ` the bundle's `base`.

# HOW TO ADD A PROCEDURAL PACK (a generator, no assets)

A procedural pack ships a pure function; the core just calls it.

1. *Write the generator.* `packs/<name>/generate.js`:
```js
   // <name> — <one line>. Ported from <repo> (<LICENSE>).
   export function generate(seed, opts) { /* … */ return "<svg …>…</svg>"; }
   export default { generate };
```
   Rules: *pure* (no DOM/Node/fetch/Date/Math.random), *zero-dep*, deterministic
   (same `seed` → byte-identical string). Hash the seed yourself (FNV-1a, or the
   source library's own hash if you're porting one — keep it exact for parity).
   Offer a `opts.monochrome` grayscale path where the algorithm allows it (the
   user likes B&W), but keep the source's native color as the default.
2. *Write `pack.json`.*
```json
   { "name": "<name>", "type": "procedural", "module": "generate.js",
     "license": "MIT", "credit": "… (MIT)", "source": "<repo url>" }
```
3. *Bundle* (optional bookkeeping). `node scripts/bundle-pack.mjs <name>` copies
   `pack.json` → `pack.bundle.json` (procedural has nothing to compile).
4. *Wire for `avatar()`.* The bundle JSON can't carry a function, so the consumer
   attaches it: `avatar({ type:"procedural", generate }, seed, opts)`. In a
   browser/specimen, load `generate.js` and build that pack object (see
   `test/build-specimen.mjs`). A bad/missing/throwing `generate` degrades to a
   1×1 svg — never throws.
5. *Verify fidelity.* If you ported an upstream library, diff your output against
   it (we verified jdenticon `d`-strings and minidenticons rects byte-identical
   vs. the npm packages). Document any deviation honestly in the file header and
   `LICENSES.md` (pixitar is a documented deviation — upstream is a
   non-deterministic Ruby asset-compositor, reimagined as a deterministic grid).

# Future packs (NOT built — source the assets/provider first)

These are out of scope until someone sources their inputs; recorded so the next
author knows the shape:

- *avataaars* (Pablo Stanley, free-for-commercial) — an *assembled* pack; needs
  its atoms cut per-category like open-peeps + a reference composition.
- *vue-color-avatar* — *assembled*; same: source its layered parts as atoms.
- *unavatar* / *dicebear-http* — a *new "network" provider type* (fetch a URL by
  seed, e.g. `https://unavatar.io/<seed>` or a DiceBear HTTP endpoint). That
  breaks the pure-string contract (`avatar()` would return an `<img>` pointing at
  a remote service), so it needs a deliberate provider design, not a pack. Note
  *DiceBear styles are licensed PER STYLE* — never bundle them under a blanket
  license.
